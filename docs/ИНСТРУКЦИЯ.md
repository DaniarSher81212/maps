## 1. Как устроена система

```
Ваш компьютер                    Oracle Cloud сервер (132.145.232.46)
──────────────                   ──────────────────────────────────────
Браузер ──────── туннель ──────► MAPS (порт 8000)
                                      │
Excel-файлы ──► дашборд ──────────────┘
                                      │
                                 PostgreSQL (БД)
                                      │
                                 Claude API (AI-функции)
```

**Что делает MAPS:**
- Принимает Excel-файлы с потребностями работ и остатками склада
- Автоматически распределяет материалы по 5 слоям (списания → склад → поставки → дефицит)
- Аварийные работы всегда получают материалы первыми
- Выдаёт Excel-отчёт с полным разбором

**Что такое туннель:**  
Cloudflare создаёт временную публичную ссылку вида `https://xxxx.trycloudflare.com`.
Через неё можно открыть MAPS с любого компьютера в интернете, не открывая порты.
URL меняется при каждом перезапуске туннеля.

## 2. Запуск на локальном компьютере

Используется для разработки и тестирования. Не нужен сервер.

### 2.1 Первый запуск (один раз)

```bash
# Перейти в папку проекта
cd ~/dev/projects/python/PythonProject

# Активировать виртуальное окружение
# Виртуальное окружение — это изолированная папка с Python и всеми пакетами проекта.
# Без него пакеты могут конфликтовать с другими проектами на компьютере.
source .venv/bin/activate

# Убедиться что .env настроен (должен быть файл с настройками БД)
cat .env
```

Минимальный `.env` для локального запуска:
```
DB_HOST=localhost
DB_PORT=5432
DB_NAME=maps_db
DB_USER=maps_user
DB_PASSWORD=ваш_пароль
ANTHROPIC_API_KEY=sk-ant-api03-...
```

### 2.2 Запуск сервера

```bash
# Из папки проекта с активированным .venv:
.venv/bin/uvicorn app.api.main:app --reload --port 8000
```

Флаг `--reload` означает: при изменении кода сервер перезапускается автоматически.
Удобно для разработки, не нужен на сервере.

После запуска вы увидите:
```
INFO:     Started server process [12345]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:8000
```

Откройте в браузере: **http://localhost:8000**

### 2.3 Остановить сервер

Нажмите **Ctrl+C** в терминале где запущен uvicorn.

### 2.4 Если порт уже занят

Ошибка: `ERROR: [Errno 98] address already in use`

```bash
# Найти и убить процесс на порту 8000
sudo fuser -k 8000/tcp

# После этого снова запустить сервер
.venv/bin/uvicorn app.api.main:app --reload --port 8000
```

## 3. Работа с сервером Oracle Cloud

Сервер работает постоянно. MAPS запускается автоматически при включении сервера.

### 3.1 Подключение к серверу

**Способ 1 — Oracle Cloud Shell (рекомендуется, самый простой):**

1. Откройте [cloud.oracle.com](https://cloud.oracle.com) в браузере
2. Нажмите иконку **`>_`** в правом верхнем углу — откроется встроенный терминал
3. В терминале наберите:

```bash
ssh ubuntu@132.145.232.46
```

Вы окажетесь внутри сервера. Никаких паролей и ключей не нужно — Oracle Cloud Shell уже авторизован.

**Способ 2 — с локального компьютера (нужен SSH-ключ):**

Oracle Cloud не принимает пароли — только SSH-ключи. Если при подключении видите:
```
ubuntu@132.145.232.46: Permission denied (publickey)
```
→ Используйте Способ 1 (Cloud Shell) или настройте SSH-ключ (см. раздел 9).

### 3.2 Управление сервисом MAPS

После подключения к серверу вы управляете MAPS через `systemctl`:

```bash
# Проверить статус (работает ли MAPS)
sudo systemctl status maps

# Запустить MAPS (если остановлен)
sudo systemctl start maps

# Остановить MAPS
sudo systemctl stop maps

# Перезапустить (например после обновления кода)
sudo systemctl restart maps
```

**Что означает вывод `systemctl status`:**

```
● maps.service - MAPS — Material Allocation & Planning System
   Active: active (running)    ← ✅ всё хорошо, MAPS работает
   Active: activating (auto-restart)  ← ⚠️ упал, пытается перезапуститься
   Active: failed              ← ❌ упал и не может запуститься
```

### 3.3 Просмотр логов

Логи помогают понять почему MAPS упал:

```bash
# Последние 30 строк лога
sudo journalctl -u maps -n 30 --no-pager

# Логи в реальном времени (выход: Ctrl+C)
sudo journalctl -u maps -f

# Логи с момента последнего запуска
sudo journalctl -u maps -b --no-pager
```

### 3.4 Запуск Cloudflare туннеля

Туннель нужен чтобы открыть MAPS с вашего компьютера.
**Важно:** Сначала убедитесь что MAPS запущен (`sudo systemctl status maps`).

```bash
# Перейти в папку проекта (обязательно!)
cd ~/maps

# Запустить туннель в фоне
bash deploy/tunnel.sh --bg

# Получить публичную ссылку
cat /tmp/maps_tunnel.url
```

Вы получите ссылку вида `https://xxxx.trycloudflare.com`.
Откройте её в браузере — это и есть дашборд MAPS.

**Если туннель не запускается или ссылка не открывается:**

```bash
# Проверить что MAPS отвечает локально
curl http://localhost:8000/api/status

# Если MAPS не отвечает — смотрим логи
sudo journalctl -u maps -n 20 --no-pager

# Если порт занят — освобождаем
sudo fuser -k 8000/tcp
sudo systemctl restart maps

# Перезапустить туннель
bash deploy/tunnel.sh --bg
cat /tmp/maps_tunnel.url
```

## 4. Ежедневная работа: полный цикл

Типичный рабочий день выглядит так:

```
1. Открыть Cloud Shell → запустить туннель → открыть дашборд
2. Загрузить обновлённые Excel-файлы (потребности, склад, поставки)
3. Нажать "Запустить распределение"
4. Скачать Excel-отчёт
5. При необходимости — задать вопрос AI-чату
```

### Шаг 1 — Открыть дашборд

```bash
# На сервере (Cloud Shell — НЕ на локальном компьютере!):
cd ~/maps
bash deploy/tunnel.sh --bg
cat /tmp/maps_tunnel.url
# → Скопировать ссылку и открыть в браузере
```

> **Частые ошибки:**
> - Команды туннеля нужно запускать **на сервере** (через Cloud Shell или SSH), а не в локальном терминале. Если видите `No such file or directory: /home/dan/maps` — вы в локальном терминале.
> - URL туннеля виден сразу в выводе `tunnel.sh --bg`, даже если `cat` команда не сработала.

### Шаг 2 — Загрузить данные

В дашборде справа — панель **«Импорт файлов»**. Раскройте нужный раздел и выберите файл.

Рекомендуемый порядок загрузки:
1. Потребности
2. Аварийные работы (если есть)
3. Складские остатки
4. Поставки
5. Списания
6. Выдано не списано

После каждой загрузки появится статистика: сколько строк загружено и сколько ошибок.

### Шаг 3 — Запустить распределение

Нажмите кнопку **«Запустить распределение»** в левой панели.
Кнопка станет неактивной, в таблице сессий появится строка со статусом 🟡 «выполняется».
Через несколько секунд статус изменится на 🟢 «завершено».

### Шаг 4 — Скачать отчёт

В таблице сессий нажмите **«Скачать Excel»** рядом с нужной сессией.
Браузер скачает файл вида `maps_results_20260524_....xlsx`.

## 5. Загрузка данных подробно

### Порядок важен!

Списания и «Выдано не списано» ссылаются на работы.
Если загрузить их **до** потребностей — строки будут пропущены с ошибкой `«Работа не найдена»`.

**Правильный порядок:**
```
1. Потребности          ← создаёт работы и материалы в БД
2. Аварийные работы     ← добавляет аварийные работы (тот же формат)
3. Складские остатки    ← загружает партии на склад
4. Поставки             ← загружает ожидаемые поставки
5. Списания             ← ссылается на работы из шага 1
6. Выдано не списано    ← ссылается на работы из шага 1
```

### Повторная загрузка (обновление данных)

Загружать файлы можно сколько угодно раз. Все типы файлов работают по принципу **полной замены**:

| Файл | Поведение |
|---|---|
| Потребности | Старые плановые потребности удаляются, загружаются новые |
| Аварийные работы | Старые аварийные потребности удаляются, загружаются новые |
| Склад | Старые партии удаляются, загружаются новые |
| Поставки | Старые поставки удаляются, загружаются новые |
| Списания | Старые записи удаляются, загружаются новые |
| Выдано не списано | Старые записи удаляются, загружаются новые |

**История сессий не удаляется** — все предыдущие результаты распределения сохраняются в БД и доступны в дашборде.

### Загрузка через curl (без браузера)

Можно загружать файлы из командной строки. Удобно для автоматизации:

```bash
# С локального компьютера (замените URL на ваш туннельный)
TUNNEL=https://xxxx.trycloudflare.com

curl -X POST $TUNNEL/api/import/requirements -F "file=@путь/к/файлу.xlsx"
curl -X POST $TUNNEL/api/import/emergency    -F "file=@путь/к/аварийные.xlsx"
curl -X POST $TUNNEL/api/import/stock        -F "file=@путь/к/склад.xlsx"
curl -X POST $TUNNEL/api/import/supplies     -F "file=@путь/к/поставки.xlsx"
curl -X POST $TUNNEL/api/import/writeoffs    -F "file=@путь/к/списания.xlsx"
curl -X POST $TUNNEL/api/import/issued       -F "file=@путь/к/выдано.xlsx"
```

Ответ при успехе:
```json
{"status": "ok", "stats": {"works": 50, "requirements": 1200, "errors": 0}}
```

Если в поле `errors` не ноль — посмотрите логи сервера:
```bash
sudo journalctl -u maps -n 50 --no-pager | grep -i error
```

### Форматы Excel-файлов

Названия колонок в файле должны совпадать с ожидаемыми. Если колонки названы иначе — строки будут пропущены без ошибки (просто не загрузятся).

**Потребности и аварийные работы:**

| Колонка | Обязательна | Пример |
|---|---|---|
| Код работы | ✅ | WO-001 |
| Тип работы | нет | Плановый ремонт |
| Филиал | ✅ | Алматы |
| Завод | ✅ | KZ01 |
| Дата начала | ✅ | 2026-06-01 |
| Приоритет | ✅ | 1 |
| Статус | ✅ | active |
| Системный номер | ✅ | MAT-001 |
| Наименование материала | ✅ | Кабель ВВГ 3х2,5 мм |
| Ед.изм | ✅ | м |
| Потребность | ✅ | 100 |
| Прогнозная цена | нет | 1200 |

**Складские остатки:**

| Колонка | Обязательна | Пример |
|---|---|---|
| Код склада | ✅ | WH-KZ01-001 |
| Тип склада | нет | Основной |
| Филиал склада | ✅ | Алматы |
| Завод склада | ✅ | KZ01 |
| Системный номер | ✅ | MAT-001 |
| Наименование материала | ✅ | Кабель ВВГ 3х2,5 мм |
| Ед.изм | ✅ | м |
| Номер партии | нет | BATCH-001 |
| Количество | ✅ | 500 |

## 6. Запуск распределения и скачивание отчёта

### Через дашборд

1. Нажмите **«Запустить распределение»**
2. Дождитесь статуса 🟢 «завершено» (обычно 5–30 секунд)
3. Нажмите **«Скачать Excel»**

### Через API (curl)

```bash
# Запустить распределение
curl -X POST http://localhost:8000/api/allocate

# Проверить статус последней сессии
curl http://localhost:8000/api/sessions

# Скачать отчёт (замените ID сессии на реальный)
curl -O -J http://localhost:8000/api/export/20260524_083028_f8db0
```

### Что означают числа в итогах сессии

```json
{
  "total_requirements": 16,   ← сколько строк потребностей обработано
  "total_allocated": 19,      ← сколько строк результатов создано (может быть > requirements,
                                 если материал берётся из нескольких партий)
  "total_deficit": 14         ← сколько позиций в дефиците
}
```

### Структура Excel-отчёта

| Лист | Что там |
|---|---|
| Распределение | Детально: работа, материал, источник (склад/поставка/списание), количество |
| Дефицит | Что не хватает, сколько, для какой работы, к какой дате нужно |
| Сводка | Агрегированная статистика по материалам и филиалам |

## 7. AI-функции

Для работы AI нужен `ANTHROPIC_API_KEY` в файле `.env`.
Без него всё остальное работает нормально, только AI-кнопки вернут ошибку 503.

### Объяснение дефицита

В дашборде внизу — синий блок **«AI-анализ дефицита»**:
1. Выберите сессию из списка
2. Выберите материал (только те, у которых есть дефицит)
3. Нажмите «Объяснить»
4. Claude объяснит на русском почему не хватило материала и что делать

### Прогноз дефицита

Кнопка **«Прогноз дефицита»** — анализирует последние 5 сессий и текущие остатки.
Результат: список материалов с уровнем риска 🔴 ВЫСОКИЙ / 🟡 СРЕДНИЙ / 🟢 НИЗКИЙ.

### RAG-чат по истории

Зелёный блок **«Вопросы по истории»** — задайте вопрос свободным текстом:
- «Какой материал чаще всего в дефиците?»
- «Когда последний раз не хватало кабеля?»
- «Сравни все сессии по количеству дефицитов»

Чат поддерживает многоходовой диалог — можно задавать уточняющие вопросы.

## 8. Обновление кода на сервере

Когда разработчик пушит изменения в GitHub — их нужно применить на сервере вручную:

```bash
# На сервере (Cloud Shell):
cd ~/maps

# Скачать последние изменения из GitHub
git pull origin main

# Перезапустить MAPS чтобы изменения вступили в силу
sudo systemctl restart maps

# Убедиться что запустился нормально
sudo systemctl status maps
```

Если после `git pull` сервис не запустился — смотрите логи:
```bash
sudo journalctl -u maps -n 30 --no-pager
```

## 9. Тестовые данные и переход на реальные

### Где хранятся тестовые файлы

Тестовые Excel-файлы лежат в папке `data/test/` на локальном компьютере:
```
data/test/
├── test_requirements.xlsx   — 13 тестовых сценариев потребностей
├── test_emergency.xlsx      — 3 аварийных работы (AV-SCN-06, 07, 08)
├── test_stock.xlsx          — тестовые остатки склада
├── test_supplies.xlsx       — тестовые поставки
├── test_writeoffs.xlsx      — тестовые списания
└── test_issued.xlsx         — тестовые «выдано не списано»
```

**Важно:** Папка `data/test/` добавлена в `.gitignore` — файлы не попадают в git.
Это сделано чтобы случайно не запушить реальные данные клиентов.
Тестовые файлы хранятся только на локальном компьютере разработчика.

### Проблема: тестовые и реальные данные смешались

**Что происходит:**  
Вы загрузили реальные потребности (199 строк) поверх тестовых данных.
В БД остались и те и другие. При запуске распределения все 215 строк
конкурируют за один и тот же (тестовый) склад — реальные результаты некорректны.

**Как определить что данные смешались:**
- Количество потребностей неожиданно большое
- В отчёте видны коды работ вида `WO-SCN-01`, `AV-SCN-06` (тестовые)
- Обеспечённость неожиданно низкая (почти всё в дефиците)

**Решение — полная очистка и загрузка только реальных данных:**

```bash
# На сервере: остановить MAPS
sudo systemctl stop maps

# Сбросить все данные через psql
sudo -u postgres psql -d maps_db -c "
TRUNCATE TABLE deficit_records, allocation_results, stock_movements,
  allocation_sessions, issued_not_written_offs, write_offs,
  supply_lines, supplies, stock_batches, warehouses,
  requirements, works, materials
  RESTART IDENTITY CASCADE;
"

# Запустить снова
sudo systemctl start maps
```

После этого загружайте только реальные файлы через дашборд в правильном порядке:
1. Потребности (реальные)
2. Аварийные работы (реальные, если есть)
3. Складские остатки (реальные)
4. Поставки (реальные)
5. Списания (реальные)
6. Выдано не списано (реальные)

### Как проверить что в БД нет тестовых данных

Тестовые работы имеют коды вида `WO-SCN-01` ... `WO-SCN-12`, `AV-SCN-06` ... `AV-SCN-08`.

```bash
# Проверить через API
curl -s http://localhost:8000/api/status
# Посмотреть на "active_works" — сколько работ в БД

# Или через psql
sudo -u postgres psql -d maps_db -c "
SELECT kod_raboty FROM works WHERE kod_raboty LIKE 'WO-SCN%' OR kod_raboty LIKE 'AV-SCN%';
"
```

Если тестовые работы нашлись — выполните очистку выше перед загрузкой реальных данных.

## 10. Работа с GitHub

### Зачем нужен GitHub

GitHub — это облачное хранилище кода. Он выполняет три роли:

1. **Резервная копия** — код не потеряется если что-то случится с компьютером
2. **История изменений** — можно посмотреть что и когда изменили, откатиться назад
3. **Мост между компьютерами** — изменения сделанные на локальном компьютере попадают на сервер через GitHub

```
Локальный компьютер  ──git push──►  GitHub  ──git pull──►  Сервер Oracle Cloud
```

### Основные команды Git

Все команды выполняются в папке проекта на **локальном компьютере**:

```bash
cd ~/dev/projects/python/PythonProject
```

#### Посмотреть текущее состояние

```bash
git status
```

Покажет:
- Какие файлы изменены (но ещё не зафиксированы)
- Какие файлы добавлены в «очередь на коммит»
- На какой ветке вы находитесь

Пример вывода:
```
On branch main
Changes not staged for commit:
  modified:   app/services/import_service.py   ← файл изменён
Untracked files:
  docs/ИНСТРУКЦИЯ.md                           ← новый файл, ещё не добавлен
```

#### Посмотреть что именно изменилось в файле

```bash
git diff app/services/import_service.py
```

Покажет построчно: что было (красным со знаком `-`), что стало (зелёным со знаком `+`).

#### Добавить файлы в «очередь на коммит»

```bash
# Добавить конкретный файл:
git add app/services/import_service.py

# Добавить несколько файлов:
git add app/services/import_service.py docs/ИНСТРУКЦИЯ.md

# Добавить всё что изменилось (осторожно — может добавить лишнее):
git add .
```

#### Зафиксировать изменения (создать коммит)

```bash
git commit -m "описание что сделали"
```

Описание пишется на любом языке. Старайтесь описывать **что** изменили и **зачем**:

```bash
# Хорошо:
git commit -m "fix: повторный импорт склада больше не падает с FK-ошибкой"
git commit -m "docs: добавил раздел про GitHub в инструкцию"

# Плохо:
git commit -m "исправления"
git commit -m "update"
```

#### Отправить изменения на GitHub

```bash
git push origin main
```

После этого изменения видны на github.com и можно обновить сервер через `git pull`.

#### Получить изменения с GitHub (на сервере)

```bash
git pull origin main
```

Скачивает всё что было запушено с локального компьютера.

### Полный цикл: внесли изменение → задеплоили

Это то что мы делаем каждый раз когда исправляем баг или добавляем новую функцию:

```bash
# 1. На локальном компьютере: смотрим что изменилось
git status

# 2. Добавляем изменённые файлы
git add имя_файла.py

# 3. Создаём коммит с описанием
git commit -m "описание изменения"

# 4. Пушим на GitHub
git push origin main

# 5. На сервере (Cloud Shell): скачиваем и перезапускаем
git pull origin main
sudo systemctl restart maps
sudo systemctl status maps
```

### Откат к предыдущей версии

Если после изменения что-то сломалось и нужно вернуть рабочую версию:

```bash

git log --oneline -10

git push origin main

git pull origin main
sudo systemctl restart maps
```

### Что НЕ попадает в GitHub

Файлы из `.gitignore` никогда не загружаются на GitHub:

| Что | Почему |
|---|---|
| `.env` | Содержит пароли и API-ключи — никогда не публиковать |
| `data/test/` | Тестовые Excel-файлы — только на локальном компьютере |
| `data/exports/` | Сгенерированные отчёты — временные файлы |
| `__pycache__/` | Скомпилированный Python — генерируется автоматически |
| `.venv/` | Виртуальное окружение — у каждого своё |

> **Важно:** Если случайно добавили `.env` в git — немедленно смените все пароли и API-ключи. Даже удалённый из git файл остаётся в истории.

## 11. Типичные ошибки и как их исправить

### Ошибка 1: «Permission denied (publickey)» при SSH

**Что видите:**
```
ubuntu@132.145.232.46: Permission denied (publickey)
```

**Причина:** Oracle Cloud не принимает пароли. Нужен SSH-ключ.

**Решение:** Используйте Oracle Cloud Shell вместо обычного SSH:
- Откройте [cloud.oracle.com](https://cloud.oracle.com)
- Нажмите иконку `>_` в правом верхнем углу
- В браузерном терминале наберите: `ssh ubuntu@132.145.232.46`

---

### Ошибка 2: Дашборд отдаёт «Not Found»

**Что видите:** Белая страница с текстом «Not Found. The requested URL was not found on the server.»

**Причина:** MAPS запущен, но приложение упало при старте и маршруты не зарегистрированы.

**Диагностика и решение:**

```bash
# На сервере: смотрим логи
sudo journalctl -u maps -n 30 --no-pager

# Возможная ошибка 1: ModuleNotFoundError: No module named 'anthropic'
# Решение: установить пакет вручную
cd ~/maps && .venv/bin/pip install anthropic
sudo systemctl restart maps

# Возможная ошибка 2: address already in use (порт занят)
# Решение:
sudo fuser -k 8000/tcp
sleep 2
sudo systemctl restart maps

# Возможная ошибка 3: --workers 2 (многопроцессный режим не работает на Oracle Cloud)
# Проверить:
grep ExecStart /etc/systemd/system/maps.service
# Если там есть --workers 2 — убрать:
sudo sed -i '/--workers/d' /etc/systemd/system/maps.service
sudo systemctl daemon-reload
sudo systemctl restart maps
```

---

### Ошибка 3: «Попытка соединения не удалась» при открытии туннельного URL

**Что видите:** Браузер говорит «не удаётся подключиться к серверу».

**Причина:** Туннель остановился (например при закрытии Cloud Shell) или MAPS упал.

**Решение:**

```bash
# На сервере:
# Шаг 1: убедиться что MAPS работает
sudo systemctl status maps
curl http://localhost:8000/api/status

# Шаг 2: если MAPS не работает — починить (см. Ошибку 2 выше)

# Шаг 3: перезапустить туннель
cd ~/maps
bash deploy/tunnel.sh --bg
cat /tmp/maps_tunnel.url
# → Скопировать новый URL и открыть в браузере
```

### Ошибка 4: FK violation при повторном импорте

**Что видите:**
```json
{"detail": "ForeignKeyViolation: update or delete on table..."}
```

**Причина (историческая):** В старых версиях MAPS при повторном импорте склада/поставок возникала ошибка FK. **Исправлено в версии после 24.05.2026** — повторный импорт работает корректно.

Если всё же получаете эту ошибку (старая версия):

```bash
# На сервере: обновить код
cd ~/maps && git pull origin main && sudo systemctl restart maps
```

### Ошибка 5: Сервис циклически перезапускается (counter at 800+)

**Что видите:**
```
Active: activating (auto-restart)
maps.service: Scheduled restart job, restart counter is at 884
```

**Причина:** MAPS постоянно падает при старте. Systemd пытается его перезапустить.

**Решение:**

```bash
# Шаг 1: смотрим причину в логах
sudo journalctl -u maps -n 20 --no-pager

# Шаг 2: останавливаем сервис чтобы он перестал циклиться
sudo systemctl stop maps

# Шаг 3: освобождаем порт если занят
sudo fuser -k 8000/tcp

# Шаг 4: тестируем запуск вручную — видим реальную ошибку
cd ~/maps
.venv/bin/uvicorn app.api.main:app --host 0.0.0.0 --port 8000
# → Смотрим что выводится в терминал

# Шаг 5: исправляем проблему (по тексту ошибки — см. другие разделы)

# Шаг 6: запускаем через systemd снова
sudo systemctl start maps
sudo systemctl status maps
```

---

### Ошибка 6: «address already in use» — порт занят

**Что видите в логах:**
```
ERROR: [Errno 98] error while attempting to bind on address ('0.0.0.0', 8000): address already in use
```

**Причина:** Предыдущий процесс uvicorn не завершился (например при `systemctl stop` воркеры зависли).

**Решение:**

```bash
# Найти и убить всё что занимает порт 8000
sudo fuser -k 8000/tcp

# Подождать 2 секунды и запустить снова
sleep 2
sudo systemctl start maps
sudo systemctl status maps
```

---

### Ошибка 7: Импорт прошёл, но часть строк пропущена

**Что видите:**
```json
{"status": "ok", "stats": {"writeoffs": 3, "errors": 0, "skipped": 10}}
```
В поле `skipped` не ноль.

**Причина:** Строки списаний или «выдано не списано» ссылаются на работы, которых нет в БД.

**Решение:** Сначала загрузите потребности (`/api/import/requirements`), потом повторите загрузку файла который давал `skipped`.

cat ~/maps/.env
