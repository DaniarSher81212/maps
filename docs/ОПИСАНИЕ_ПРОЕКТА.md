## 1. Что такое MAPS и зачем он нужен

MAPS — система автоматического распределения строительных материалов.

### Бизнес-задача

На предприятии одновременно ведутся сотни строительно-монтажных работ (СМР).
У каждой работы есть список нужных материалов с количествами — это **потребность**.

Материалы хранятся:
- **На складах** — конкретные партии с ценой и датой поступления
- **В поставках** — заказаны у поставщиков, ещё едут («в пути»)
- **Уже списаны** — оформлены документально на работу в SAP (система учёта)
- **Выданы, но не списаны** — физически на объекте, документ ещё не оформлен

**Проблема без MAPS:** плановый отдел вручную в Excel разбирает: кому дать какой материал.
Это часами, с ошибками, непрозрачно.

**Решение MAPS:** 5+1-слойный алгоритм автоматически закрывает потребности работ,
соблюдая приоритет (аварийные → по дате → плановые), и выдаёт Excel-отчёт с
процентом обеспечённости и списком «К закупу».

Дополнительно: после первого запуска пользователь может согласовать межфилиальные
перемещения и запустить распределение повторно — система учтёт их как реальный источник.

### 4.2 `app/db/database.py` — Подключение к PostgreSQL

**Назначение:** Создаёт соединение с PostgreSQL и управляет транзакциями.

**Три ключевых объекта:**

**1) `engine` — движок (пул соединений)**
```python
engine = create_engine(
    settings.db_url,
    pool_size=5,         # 5 постоянных соединений
    max_overflow=10,     # ещё до 10 временных при пике нагрузки
    pool_pre_ping=True,  # проверять соединение перед использованием
    echo=settings.is_development,  # выводить SQL в лог при разработке
)
```
Пул соединений нужен для производительности: открытие нового TCP-соединения к PostgreSQL
занимает ~20 мс. Без пула при 100 запросах/сек — 2 секунды только на соединения.

**2) `SessionLocal` — фабрика сессий**
```python
SessionLocal = sessionmaker(
    bind=engine,
    autocommit=False,  # изменения только при явном commit()
    autoflush=False,   # не отправлять SQL до commit()
)
```
`autoflush=False` важно: при `True` SQLAlchemy вставляет flush перед каждым SELECT,
что может вызвать неожиданные INSERT в середине транзакции.

**3) `get_session()` — контекстный менеджер**
```python
@contextmanager
def get_session() -> Generator[Session, None, None]:
    session = SessionLocal()
    try:
        yield session      # отдаём сессию в блок with
        session.commit()   # успех → сохраняем всё
    except Exception:
        session.rollback() # ошибка → откатываем всё
        raise
    finally:
        session.close()    # всегда закрываем (возвращаем в пул)
```

**Использование везде в коде:**
```python
with get_session() as session:
    work = session.get(Work, work_id)
    session.add(new_work)
    # commit автоматически при выходе из with
```

**Почему не используем FastAPI `Depends` для БД?**
Некоторые операции (импорт, распределение) запускаются из CLI или фоновых заданий,
где нет HTTP-запроса. `get_session()` работает везде — и в HTTP-обработчиках, и в CLI.

Современный синтаксис даёт IDE-автодополнение и проверку типов Pyright:

# Старый синтаксис (SQLAlchemy 1.x):

# Новый синтаксис (SQLAlchemy 2.x):
kod_raboty: Mapped[str] = mapped_column(String(100), nullable=False)

**Ключевые поля и почему они именно такие:**

`Work.is_emergency` — булево. Аварийные работы идут перед всеми обычными.
`Work.data_nachala` — ГЛАВНЫЙ критерий сортировки (не `prioritet`!). Кто начинается раньше — первый.
`Work.prioritet` — дополнительный для обычных работ, игнорируется у аварийных.
`Requirement.prognosnaya_tsena` — прогнозная цена. Нужна для расчёта % обеспечённости по стоимости.
`Requirement.raspredeleno` — заполняется алгоритмом. Накапливается в памяти, потом пишется в БД.
`StockBatch.dostupno` — доступный остаток. Уменьшается алгоритмом в `_batch_cache`, в конце — UPDATE.
`StockBatch.data_postupleniya` — для FIFO: старые партии расходуются первыми.
`Supply.filial` — поставки привязаны к ФИЛИАЛУ, не к заводу. Ключевое бизнес-правило.
`AllocationResult.is_possible` — `True` = анализ («возможное»), `False` = факт. Только `False` меняет остатки.
`AllocationResult.istochnik` — код источника:
- `"spisanie"` — Слой 1
- `"vydano"` — Слой 2
- `"sklad"` — Слой 3 (свой завод/филиал)
- `"odobren_perenos"` — Слой 3в (согласованное межфилиальное)
- `"vozmozhnoe_sklad"` — Слой 3б (аналитика, `is_possible=True`)
- `"postavka"` — Слой 4

`ApprovedTransfer.kolichestvo` — исходное согласованное количество (не меняется).
`ApprovedTransfer.dostupno` — доступный остаток. Сбрасывается перед каждым запуском.
`ApprovedTransfer.from_warehouse_id` — склад-источник (у другого филиала).
`ApprovedTransfer.to_filial` — филиал-получатель (куда идут материалы).

### 4.4 `app/models/schemas.py` — Pydantic-схемы для валидации

**Назначение:** Проверяет каждую строку Excel перед записью в БД.
Если данные некорректны — понятное сообщение об ошибке, строка пропускается.

**Чем отличается от ORM-моделей?**
```
ORM (models.py)       → описывает ТАБЛИЦЫ в PostgreSQL
Pydantic (schemas.py) → описывает ДАННЫЕ при вводе (Excel-строки, API-запросы)
```

**Почему `Decimal`, а не `float`?**
```python
# float — ошибка округления:
>>> 0.1 + 0.2
0.30000000000000004

# Decimal — точность:
>>> Decimal("0.1") + Decimal("0.2")
Decimal("0.3")
```
В финансовых расчётах (стоимости, количества) это критично.

**Вспомогательные функции верхнего уровня:**

`_parse_decimal_ru(v)` — разбирает число в русском формате: пробел как разделитель тысяч,
запятая как разделитель дробной части. Примеры:
```python
_parse_decimal_ru("1 234,56")  → Decimal("1234.5600")
_parse_decimal_ru("100,5")     → Decimal("100.5000")
_parse_decimal_ru(None)        → Decimal("0")
```
Алгоритм: убрать пробелы → заменить запятую на точку → `Decimal(s).quantize("0.0001")`.

`_parse_date_ru(v)` — разбирает дату в нескольких форматах:
```python
_parse_date_ru("28.05.2026")   → date(2026, 5, 28)   # ДД.ММ.ГГГГ (основной)
_parse_date_ru("2026-05-28")   → date(2026, 5, 28)   # ISO (запасной)
_parse_date_ru(datetime(...))  → date(...)            # уже объект
_parse_date_ru(None)           → None
```
Пробует форматы последовательно: `"%d.%m.%Y"` → `"%Y-%m-%d"` → `"%d/%m/%Y"`.

Эти функции используются во всех `field_validator` схем вместо прямого `Decimal(v)`,
гарантируя, что любой Excel-файл с русским форматом чисел и дат будет принят.

**`field_validator` — нормализация Excel-данных:**
```python
@field_validator("kod_raboty", mode="before")
@classmethod
def strip_and_upper(cls, v):
    s = str(v).strip()
    if s.endswith(".0"):
        s = s[:-2]  # "WO12345.0" → "WO12345" (Excel форматирует как float)
    return s
```

**`model_validator` — проверка связанных полей:**
```python
@model_validator(mode="after")
def check_dates(self):
    if self.data_nachala and self.data_okonchaniya:
        if self.data_nachala > self.data_okonchaniya:
            raise ValueError("Дата начала не может быть позже даты окончания")
    return self
```

**Все схемы импорта:**

| Схема | Файл | Обязательные поля |
|---|---|---|
| `WorkImportRow` | потребности (требования) | kod_raboty, sys_nomer_materiala, potrebnost |
| `WorkListImportRow` | перечень работ | kod_raboty (остальные необязательны) |
| `StockImportRow` | складские остатки | kod_sklada, sys_nomer, kolichestvo |
| `SupplyImportRow` | поставки | dogovor, sys_nomer, kolichestvo |
| `WriteOffImportRow` | фактические списания | kod_raboty, sys_nomer, kolichestvo |
| `IssuedNotWrittenOffImportRow` | выдано не списано | kod_raboty, sys_nomer, kolichestvo |
| `ApprovedTransferImportRow` | согласованные перемещения | sys_nomer, kod_sklada_istochnik, to_filial, kolichestvo |

`ApprovedTransferImportRow` — новая схема для Слоя 3в. Поле `kolichestvo` валидируется
через `_parse_decimal_ru` (поддерживает русский формат). `sys_nomer_materiala` и
`kod_sklada_istochnik` нормализуются через `clean_string` (убираем `.0` из float-кодов).

### 4.5 `app/repositories/base.py` — Базовый репозиторий

**Назначение:** Паттерн Repository — изолирует SQL-запросы от бизнес-логики.

**Что такое паттерн Repository?**
```python
# БЕЗ паттерна (плохо — SQL прямо в бизнес-логике):
def allocate(session, work_id):
    work = session.query(Work).filter(Work.id == work_id).first()
    materials = session.query(Material).join(Requirement)...

# С ПАТТЕРНОМ (хорошо — логика работает с объектами):
def allocate(work_repo, material_repo):
    work = work_repo.get_by_id(work_id)
    materials = material_repo.get_for_work(work_id)
```
Преимущество: при смене БД меняем только репозиторий, алгоритм не трогаем.

**Generic[T] — универсальный класс:**
```python
T = TypeVar("T", bound=Base)

class BaseRepository(Generic[T]):
    # Один класс работает с любой ORM-моделью
```

**CRUD-методы:**
- `get_by_id(id)` — SELECT по первичному ключу
- `get_all()` — SELECT * (осторожно с большими таблицами)
- `add(obj)` — добавить в сессию (не в БД, нужен commit)
- `add_all(list)` — массовая вставка
- `delete(obj)` — удалить
- `flush()` — отправить изменения в БД без коммита (нужен для получения ID)
- `count()` — COUNT(*)

### 4.6 `app/repositories/material_repository.py` — Репозитории материалов

Содержит **6 репозиториев**: `MaterialRepository`, `StockBatchRepository`,
`SupplyRepository`, `ApprovedTransferRepository`, `WriteOffRepository`,
`IssuedNotWrittenOffRepository`.

#### `MaterialRepository`

`get_by_sys_nomer(sys_nomer)` — поиск материала по SAP-номеру.

`get_or_create(sys_nomer, naimenovanie, ...)` — главный метод.
Материалы встречаются в разных Excel-файлах. Если уже есть — не дублируем.
Если пришли с новым наименованием — обновляем (только если поле было пустым).

`get_id_map()` — возвращает `{sys_nomer: id}` для **быстрого поиска при импорте**.
Без этого: импорт 10 000 строк = 10 000 SELECT-запросов.
С этим: один SELECT, потом поиск в словаре за O(1).

#### `StockBatchRepository`

`get_available_for_material(material_id, min_qty)` — все доступные партии материала
по всем складам, отсортированные FIFO (`data_postupleniya ASC`).

`get_available_by_warehouse_priority(material_id, zavod, filial)` — ключевой метод для Слоя 3.
Возвращает партии, разбитые на три группы:
```python
{
    "zavod":   [...],  # тот же завод — высший приоритет
    "filial":  [...],  # тот же филиал — средний приоритет
    "prochee": [...],  # другие филиалы — только для анализа (Слой 3б)
}
```
Разделение на Python (не SQL) — один запрос к БД, потом быстрая группировка в памяти.

`get_batches_for_warehouse_material(warehouse_id, material_id, min_qty)` — партии
**конкретного склада** для конкретного материала в порядке FIFO.
Используется в Слое 3в (согласованные перемещения): нам нужны именно партии
склада-источника, указанного в `ApprovedTransfer.from_warehouse_id`.

`reset_dostupno()` — восстанавливает `dostupno = kolichestvo` у всех партий.
Вызывается перед каждым запуском алгоритма.

`bulk_create(batches)` — массовая вставка партий при импорте склада.

#### `SupplyRepository`

`get_available_lines_for_material(material_id, filial)` — строки поставок.
**Ключевое бизнес-правило:** фильтруем по `filial` поставки = `filial` работы.
Поставки идут на ФИЛИАЛ, не на конкретный завод.

`reset_dostupno()` — то же что у `StockBatch`, но для строк поставок.

#### `ApprovedTransferRepository`

Управляет таблицей `approved_transfers` — согласованными межфилиальными перемещениями.

`get_grouped_by_material_filial()` — загружает все записи одним SELECT и группирует
в словарь `{(material_id, to_filial): [ApprovedTransfer, ...]}`.
Это основной паттерн доступа в алгоритме: «дай мне все согласования для этого материала в этот филиал».

`reset_dostupno()` — сбрасывает `dostupno = kolichestvo` перед каждым запуском.
Без этого повторный запуск увидит исчерпанные разрешения.

`delete_all()` — удаляет все записи. Вызывается при загрузке нового файла согласований
(каждый импорт полностью заменяет предыдущий набор).

`count()` — количество записей. Используется в статусе и диагностике.

#### `WriteOffRepository`

`get_all_grouped_by_work_material()` — загружает ВСЕ списания одним SELECT
и группирует в `{(work_id, material_id): [WriteOff, ...]}`.

**Зачем грузить всё сразу?** Алгоритм обрабатывает тысячи потребностей.
Если делать SELECT для каждой — N+1 запросов. Один SELECT + словарь в памяти — быстрее в 100 раз.

#### `IssuedNotWrittenOffRepository`

Аналогично `WriteOffRepository`, но для Слоя 2 («Выдано не списано»).

### 4.7 `app/repositories/work_repository.py` — Репозиторий работ и потребностей

#### `WorkRepository`

`get_or_create(kod_raboty, is_emergency, ...)` — создаёт или возвращает работу.
`is_emergency=True` — при импорте аварийных работ: если работа уже есть — обновляет флаг.

`get_active_sorted()` — работы в правильном порядке распределения. Использует SQL `CASE`:
```sql
ORDER BY
    works.is_emergency DESC,                              -- аварийные первыми
    works.data_nachala ASC NULLS LAST,                    -- по дате начала
    CASE WHEN NOT is_emergency THEN prioritet ELSE 0 END  -- приоритет (только обычных)
```

`get_kod_map()` — `{kod_raboty: id}` для O(1) поиска при импорте.

#### `RequirementRepository`

`upsert(work_id, material_id, potrebnost, prognosnaya_tsena)` — создаёт или суммирует.
**Почему суммируем?** В Excel один материал может встречаться в нескольких строках
для одной работы (разные подрядчики, секции объекта). Бизнес-правило: суммируем.

`get_for_allocation()` — ГЛАВНЫЙ запрос алгоритма. Возвращает
`[(Requirement, Work, Material), ...]` в порядке распределения:
```sql
ORDER BY
    works.is_emergency DESC,
    works.data_nachala ASC NULLS LAST,
    CASE WHEN NOT is_emergency THEN prioritet ELSE 0 END ASC,
    works.filial ASC,
    works.kod_raboty ASC,
    materials.sys_nomer ASC
```

`reset_allocation()` — обнуляет `raspredeleno = 0`, `deficit = 0`.
Вызывается в начале каждого запуска. Без сброса — повторный запуск накапливал бы значения.

### 4.8 `app/services/import_service.py` — Импорт из Excel

**Назначение:** Читает Excel-файлы и записывает данные в PostgreSQL.
Содержит **8 функций импорта** для 8 типов файлов.

**Общий принцип работы:**
```
Excel → pandas (dtype=str, keep_default_na=False)
     → _rename_columns(column_map)
     → for row: Pydantic.validate()   ← _parse_decimal_ru / _parse_date_ru
     → get_or_create / upsert
     → session.flush() каждые 500 строк
     → session.commit() при выходе из get_session()
```

**Почему `dtype=str` в pandas?**
```python
df = pd.read_excel(file_path, dtype=str, keep_default_na=False)
```
Без `dtype=str` pandas угадывает типы:
- `"10012345"` → `10012345.0` (float!) — ломает SAP-номера
- `"28.05.2026"` → `Timestamp(...)` — сложно передать в Pydantic
- Пустые ячейки → `NaN` — вызывают ошибки в `str.strip()`

`keep_default_na=False` — пустые ячейки остаются `""`, не `NaN`.

**`column_map` — маппинг колонок Excel → поля схемы:**
```python
REQUIREMENTS_COLUMN_MAP = {
    "Код работы":      "kod_raboty",
    "Системный номер": "sys_nomer_materiala",
    "Потребность":     "potrebnost",
    ...
}
```
Если клиент изменит заголовки Excel — меняем только этот словарь.

**`APPROVED_TRANSFERS_COLUMN_MAP`** поддерживает альтернативные заголовки:
```python
APPROVED_TRANSFERS_COLUMN_MAP = {
    "Системный номер":    "sys_nomer_materiala",
    "Склад-источник":     "kod_sklada_istochnik",
    "Филиал-получатель":  "to_filial",
    "Кол-во согласовано": "kolichestvo",
    "Возможное кол-во":   "kolichestvo",   # альтернативный заголовок
    "Куда (филиал)":      "to_filial",     # альтернативный заголовок
}
```
Это позволяет загружать файл прямо из листа «Возможное перемещение»
(где заголовки могут отличаться от стандарта).

#### `import_requirements()` — главный импорт потребностей

1. Полный сброс операционных данных (кроме `works`)
2. Предзагрузка словарей `{kod_raboty: id}` и `{sys_nomer: id}` в память
3. Для каждой строки: валидация → `get_or_create` Work → `get_or_create` Material → `upsert` Requirement

**Почему `works` НЕ очищается:**
`works` — мастер-данные. Загрузка «Перечня работ» (`import-works`) кладёт туда даты.
Очистка уничтожила бы их. `get_or_create` предотвращает дубли.

#### `import_emergency_works()` — аварийные работы

Формат файла **такой же**, как обычные потребности (`REQUIREMENTS_COLUMN_MAP`).
Единственное отличие: `is_emergency=True` при создании работ.
Удаляет только аварийные работы (не все).

#### `import_stock()` — складские остатки

**Полная замена:** удаляет все старые партии и загружает заново («снимок склада»).
`dostupno = kolichestvo` при создании — весь объём изначально доступен.

#### `import_supplies()` — поставки

Группировка строк Excel по `dogovor_key`:
```python
dogovor_key = f"{dogovor}_{kod_sklada}_{data_postavki}"
```
Несколько строк одного договора → один `Supply` + несколько `SupplyLine`.

#### `import_writeoffs()` — фактические списания

Если работа не найдена — строка пропускается с `skipped += 1`.
Сначала нужно загрузить потребности. Если материал не найден — создаётся автоматически.

#### `import_issued_not_written_off()` — выдано не списано

Аналогично `import_writeoffs()`. Поле `warehouse_id` только информативное —
алгоритм при обработке этого слоя **не изменяет остатки склада**.

#### `import_works()` — перечень работ (мастер-данные)

**Upsert без очистки:** обновляет существующие работы, создаёт новые.
Обновляет только непустые поля: если в файле не заполнено — существующие данные не затираются.
Возвращает `{"created": N, "updated": K, "errors": M}`.

#### `import_approved_transfers()` — согласованные перемещения (Слой 3в)

Алгоритм:
1. `transfer_repo.delete_all()` — удалить предыдущие согласования
2. Загрузить `{sys_nomer: id}` и `{kod_sklada: id}` в память
3. Для каждой строки: валидация `ApprovedTransferImportRow` → найти `material_id` →
   найти `warehouse_id` → создать `ApprovedTransfer(dostupno = kolichestvo)`
4. `session.flush()` каждые 500 строк

Возвращает `{"created": N, "errors": K, "skipped": M}`.
`skipped` — строки где материал или склад не найдены в БД.

### 4.9 `app/allocation/engine.py` — Ядро: алгоритм распределения

**Это самый важный файл проекта.** Класс `AllocationEngine` реализует 5+1-слойный алгоритм.

#### Вспомогательный класс `_WarehouseAccumulator`

**Проблема:** один склад может иметь несколько партий с разными ценами.
В отчёте нужна **одна строка на склад** со **средней взвешенной ценой (WAC)**.

```
Склад W-001:
  Партия 001: 100 м × 1500 тг/м = 150 000 тг
  Партия 002:  50 м × 1600 тг/м =  80 000 тг
  ─────────────────────────────────────────────
  Итого:      150 м × 1533 тг/м = 230 000 тг  ← WAC
```

**Как считается WAC:**
```python
avg_cost = weighted_cost_sum / total_qty
# = (100×1500 + 50×1600) / (100 + 50) = 230000 / 150 = 1533.33
```

Накопитель собирает партии через `acc.add(qty, cost)`,
потом создаётся одна строка результата с агрегированными данными.

Параметр `is_possible` — передаётся при создании накопителя: `False` для Слоёв 3 и 3в,
`True` для Слоя 3б. Влияет на поле `AllocationResult.is_possible`.

#### `EPSILON = Decimal("0.0001")`

Минимальное значимое количество. Всё что меньше считается нулём.
Нужно чтобы не распределять «5e-7 метров кабеля» из-за ошибок округления Decimal.

#### `AllocationEngine.__init__` — инициализация

```python
def __init__(self, session: Session, session_id: Optional[str] = None):
    # Репозитории — доступ к 6 видам данных
    self.req_repo      = RequirementRepository(session)
    self.batch_repo    = StockBatchRepository(session)
    self.supply_repo   = SupplyRepository(session)
    self.writeoff_repo = WriteOffRepository(session)
    self.issued_repo   = IssuedNotWrittenOffRepository(session)
    self.approved_repo = ApprovedTransferRepository(session)  # ← Слой 3в

    # Буферы для batch-INSERT в конце
    self._allocation_buffer = []   # AllocationResult
    self._movement_buffer   = []   # StockMovement
    self._deficit_buffer    = []   # DeficitRecord

    # Кэши актуальных остатков в памяти (UPDATE в БД — только в конце)
    self._batch_cache    = {}   # {batch_id: dostupno}
    self._supply_cache   = {}   # {supply_line_id: dostupno}
    self._approved_qty_cache = {}  # {approved_transfer_id: dostupno}

    # Предзагруженные данные слоёв (один SELECT в начале, потом O(1))
    self._writeoff_cache  = {}  # {(work_id, material_id): [WriteOff]}
    self._issued_cache    = {}  # {(work_id, material_id): [IssuedNotWrittenOff]}
    self._approved_cache  = {}  # {(material_id, to_filial): [ApprovedTransfer]}

    # Статистика
    self._stats = {
        "requirements_processed": 0,
        "allocated_writeoff":  0,
        "allocated_issued":    0,
        "allocated_warehouse": 0,
        "allocated_approved":  0,   # ← Слой 3в
        "possible_warehouse":  0,
        "allocated_supply":    0,
        "deficit_records":     0,
    }
```

**Зачем буферы и кэши?**
При 5000 потребностях построчный INSERT/UPDATE = 5000+ запросов.
`bulk_save_objects()` и batch UPDATE в конце = несколько запросов. В 10–50 раз быстрее.

#### `AllocationEngine.run()` — точка входа

```
1. Создать AllocationSession (статус "running")
2. Загрузить слои 1 и 2 в _writeoff_cache и _issued_cache (один SELECT каждый)
3. Загрузить Слой 3в в _approved_cache + approved_repo.reset_dostupno()
4. Сбросить предыдущие результаты (raspredeleno=0, dostupno=kolichestvo)
5. Получить все потребности в порядке распределения (get_for_allocation)
6. Для каждой потребности → _process_requirement()
7. batch-INSERT: _flush_buffers_to_db()
8. UPDATE остатков: _update_availability_in_db()
9. Обновить AllocationSession: статус "completed", статистика
```

При ошибке на шагах 5–9 → сессия помечается `"failed"`, ошибка пробрасывается.

#### `_process_requirement(req, work, material)` — обработка одной потребности

```python
remaining = req.potrebnost - req.raspredeleno  # непокрытый остаток

# Завершённые работы (data_okonchaniya < сегодня):
# только слои 1 и 2, склад и поставки — для будущих
if work.is_completed:
    remaining = self._apply_writeoff_layer(...)
    remaining = self._apply_issued_layer(...)
    self._record_deficit(...)
    return

# Активные работы — все слои:
remaining = self._apply_writeoff_layer(req, work, material, remaining)        # Слой 1
remaining = self._apply_issued_layer(req, work, material, remaining)           # Слой 2
remaining = self._allocate_from_warehouse(req, work, material, remaining)      # Слой 3
if remaining >= EPSILON and self._approved_cache:
    remaining = self._allocate_from_approved_transfers(req, work, material, remaining)  # Слой 3в
self._record_possible_from_other_filial(req, work, material, remaining)        # Слой 3б
remaining = self._allocate_from_supplies(req, work, material, remaining)       # Слой 4
self._record_deficit(req, work, material, remaining)                           # Слой 5
```

Слой 3б (`_record_possible`) не уменьшает `remaining` — это только аналитика.

#### `_apply_writeoff_layer` — Слой 1 (фактические списания)

```python
key = (work.id, material.id)
writeoffs = self._writeoff_cache.get(key, [])  # O(1) из памяти
total_qty = sum(wo.kolichestvo for wo in writeoffs)
qty = min(remaining, total_qty)
```
Создаётся одна строка `AllocationResult` с `istochnik="spisanie"`.
`warehouse_id=None` — материал уже списан, к складу не привязан.

#### `_apply_issued_layer` — Слой 2 (выдано не списано)

Аналогично Слою 1. `istochnik="vydano"`. Остатки склада **не меняем**.

#### `_allocate_from_warehouse` — Слой 3 (склад)

1. Получить три группы партий: `"zavod"`, `"filial"`, `"prochee"`
2. Обрабатывать только `"zavod"` и `"filial"` (в порядке приоритета)
3. Для каждой партии группы:
   - Взять `min(remaining, _batch_cache[batch.id])`
   - Обновить `_batch_cache` (не БД!)
   - Создать `StockMovement` (детальная запись для листа «Движение склада»)
   - Добавить в `_WarehouseAccumulator` для этого склада
4. После всех партий группы — одна `AllocationResult` на каждый склад (WAC)

`_get_batch_available(batch)` — читает из `_batch_cache` (кэш) или из `batch.dostupno` (БД):
```python
def _get_batch_available(self, batch: StockBatch) -> Decimal:
    return self._batch_cache.get(batch.id, batch.dostupno)
```

#### `_record_possible_from_other_filial` — Слой 3б (аналитика)

Берёт группу `"prochee"`. `is_possible=True` — не меняет `remaining` и `dostupno`.
`istochnik="vozmozhnoe_sklad"`, `tip_raspredeleniya="vozmozhnoe"`.
Использует `batch.dostupno` напрямую (не из кэша — чужой склад не трогался).

#### `_allocate_from_approved_transfers` — Слой 3в (согласованные перемещения)

```python
key = (material.id, work.filial or "")
transfers = self._approved_cache.get(key, [])
for transfer in transfers:
    approved_available = self._get_approved_available(transfer)
    take_limit = min(remaining, approved_available)

    # Берём партии склада-источника (FIFO)
    batches = self.batch_repo.get_batches_for_warehouse_material(
        warehouse_id=transfer.from_warehouse_id,
        material_id=material.id,
    )
    # ... уменьшаем _batch_cache, создаём StockMovement ...
    # ... обновляем _approved_qty_cache[transfer.id] ...
    # Создаём AllocationResult с istochnik="odobren_perenos", is_possible=False
```

Ключевые отличия от Слоя 3б:
- Остатки склада-источника **уменьшаются** (`_batch_cache`)
- `remaining` **уменьшается** (потребность реально закрывается)
- `is_possible=False` — это фактическое распределение

`_get_approved_available(transfer)` — читает из кэша или из БД:
```python
def _get_approved_available(self, transfer: ApprovedTransfer) -> Decimal:
    return self._approved_qty_cache.get(transfer.id, transfer.dostupno)
```

#### `_allocate_from_supplies` — Слой 4 (поставки)

Фильтрует по `filial=work.filial` — бизнес-правило.
Каждая строка поставки → отдельная строка `AllocationResult` с `istochnik="postavka"`.
Обновляет `_supply_cache[line.id]`.

#### `_record_deficit` — Слой 5 (дефицит)

```python
estimated_cost = deficit_qty × req.prognosnaya_tsena
```
Стоимость «К закупу» по прогнозной цене из заявки. Запись в `DeficitRecord`.

#### `_flush_buffers_to_db` — batch-INSERT

```python
self.session.bulk_save_objects(self._allocation_buffer)  # все AllocationResult
self.session.bulk_save_objects(self._movement_buffer)    # все StockMovement
self.session.bulk_save_objects(self._deficit_buffer)     # все DeficitRecord
self.session.flush()
```

#### `_update_availability_in_db` — обновление остатков

```python
for batch_id, new_available in self._batch_cache.items():
    batch = self.session.get(StockBatch, batch_id)
    batch.dostupno = new_available

for line_id, new_available in self._supply_cache.items():
    line = self.session.get(SupplyLine, line_id)
    line.dostupno = new_available

for transfer_id, new_available in self._approved_qty_cache.items():
    transfer = self.session.get(ApprovedTransfer, transfer_id)
    transfer.dostupno = new_available
```
Обновляем только задействованные записи (не полный UPDATE таблицы).

### 4.10 `app/services/export_service.py` — Экспорт в Excel

**Назначение:** Формирует многолистовой Excel-отчёт из данных PostgreSQL.

**Вспомогательные функции форматирования:**

`_fmt_num(val, decimals=2)` — форматирует число в русском формате:
```python
_fmt_num(1234.56)      → "1234,56"    # запятая как разделитель
_fmt_num(1234.5678, 4) → "1234,5678"
_fmt_num(None)         → ""
_fmt_num(float("nan")) → ""
```
Зачем строка, а не число? Excel открывается у пользователей с русской локалью.
Записывая строку с запятой, гарантируем корректный вид независимо от настроек системы.

`_fmt_date(val)` — форматирует дату в формате ДД.ММ.ГГГГ:
```python
_fmt_date(date(2026, 5, 28))      → "28.05.2026"
_fmt_date(pd.Timestamp(...))      → "28.05.2026"
_fmt_date("2026-05-28")           → "28.05.2026"  # ISO → ДД.ММ.ГГГГ
_fmt_date(None)                   → ""
```

**Функция `export_allocation_results(session_id)`** — точка входа.
Открывает одну сессию БД, выполняет 10 SQL-запросов, записывает до 11 листов.

**Почему pandas, а не openpyxl напрямую?**
pandas агрегирует данные (groupby, merge). openpyxl — низкоуровневая работа с ячейками.
Связка: pandas строит DataFrame → openpyxl записывает в файл.

**Все листы отчёта:**

#### Лист 1: «Распределение» — главная широкая таблица

Функция `_get_wide_allocation_df(session, session_id)`.

Подход: **разворачиваем слои в колонки** (pivot-like без SQL PIVOT):
```
requirement_id | Сп: К-во | Сп: Цена | Выд: К-во | Ск: К-во | Ск: Цена | Од: К-во | Пост: К-во | К закупу | %
─────────────────────────────────────────────────────────────────────────────────────────────────────────────
R-001          | 60       | 1500     | 10        | 30       | 1533     | 20       | 0          | 0        | 100%
R-002          | 0        | 0        | 0         | 50       | 1450     | 0        | 20         | 30       | 56%
```

Алгоритм в `_get_wide_allocation_df`:
```
1. SELECT все потребности JOIN work JOIN material
2. SELECT все AllocationResult WHERE is_possible=FALSE
3. _agg_layer("spisanie")      → df_sp  (qty, avg_price, summa)
4. _agg_layer("vydano")        → df_vd
5. _agg_layer("sklad")         → df_sk  (+ WAC)
6. _agg_layer("odobren_perenos") → df_od  (← Слой 3в)
7. _agg_layer("postavka")      → df_pv  (+ dogovora, postavshchiki через ", ".join)
8. LEFT JOIN через pandas.merge: потребности ← слои
9. covered_summa = sp + vd + sk + od + pv
10. coverage_pct = covered_summa / (potrebnost × prognosnaya_tsena) × 100
11. k_zakupu_qty  = max(0, potrebnost - raspredeleno)
12. Применить _fmt_num ко всем числовым колонкам
13. Применить _fmt_date к колонкам дат
```

`_agg_layer(istochnik)` — внутренняя функция, агрегирует строки одного источника:
```python
def _agg_layer(istochnik: str) -> pd.DataFrame:
    rows = [r for r in all_results if r.istochnik == istochnik]
    # GROUP BY requirement_id → sum(kolichestvo), wavg(srednyaya_stoimost), sum(summa)
```

`_merge_layer(df, df_layer, prefix)` — LEFT JOIN основного датафрейма с агрегированным:
```python
def _merge_layer(df_main, df_layer, prefix):
    return df_main.merge(df_layer, on="requirement_id", how="left")
    # Заполняет NaN нулями для потребностей без данного слоя
```

#### Лист 2: «Движение склада»

Функция `_get_movement_df(session, session_id)`.
JOIN: `stock_movements ← warehouses ← materials ← works`.
Одна строка = одно списание одной партии на одну работу.

#### Лист 3: «Остатки складов после распределения»

Функция `_get_warehouse_balances_df(session)`.
`kolichestvo` (исходный) → `kolichestvo - dostupno` (распределено) → `dostupno` (остаток).

#### Лист 4: «Возможное перемещение»

Функция `_get_possible_movements_df(session, session_id)`.
`WHERE is_possible=TRUE` — что МОЖНО перебросить из других филиалов.

#### Лист 5: «Одобренные перемещения» (условный)

Функция `_get_approved_transfers_df(session, session_id)`.
`WHERE istochnik='odobren_perenos'` — что реально взяли через Слой 3в.
Лист добавляется в файл только если `not df_approved.empty`.

#### Лист 6: «Обеспеченность»

Функция `_get_coverage_by_work_df(session, session_id)`.
GROUP BY work: итоговая стоимость потребности, покрытие, дефицит, % обеспечённости.

#### Листы 7–8: «В пути» и «Не распред. в пути»

`_get_in_transit_allocated_df` — строки поставок с `AllocationResult` (зарезервированы).
`_get_in_transit_unallocated_df` — строки поставок где `dostupno > 0` (свободные).

#### Листы 9–11: Исходные данные

`_get_source_requirements_df` — все потребности до распределения (для аудита).
`_get_source_stock_df` — начальные остатки складов.
`_get_source_supplies_df` — все строки поставок.

**`_write_sheet(writer, df, sheet_name)`** — записывает DataFrame в лист с автошириной колонок.
Если `df.empty` — создаёт лист с текстом «Нет данных».

### 4.14 `app/api/routes/import_.py` — Импорт через API

**8 эндпоинтов**, каждый принимает файл через `multipart/form-data`.

Вспомогательная функция `_save_upload(file)`:
```python
async def _save_upload(file: UploadFile) -> Path:
    content = await file.read()          # асинхронное чтение
    suffix = Path(file.filename).suffix  # .xlsx или .xls
    with tempfile.NamedTemporaryFile(suffix=suffix, delete=False) as tmp:
        tmp.write(content)
        return Path(tmp.name)
```
Зачем временный файл? `import_service` использует `pd.read_excel(path)` —
ожидает путь к файлу, не поток байт.

Каждый маршрут:
```python
@router.post("/import/requirements")
async def import_requirements_endpoint(file: UploadFile = File(...)):
    tmp = await _save_upload(file)
    try:
        stats = import_requirements(tmp)
        return {"status": "ok", "file": file.filename, "stats": stats}
    except Exception as e:
        raise HTTPException(status_code=422, detail=str(e))
    finally:
        tmp.unlink(missing_ok=True)  # удаляем в любом случае
```

### 4.17 `app/ai/deficit_analyzer.py` — AI-объяснение дефицита

**Как работает:**
1. Из БД извлекает: работы в дефиците, что дал каждый слой, складские остатки

## 7. Алгоритм распределения — детально

### Порядок обработки работ

```
1. Аварийные (is_emergency=TRUE) — по data_nachala ASC NULLS LAST
2. Обычные    (is_emergency=FALSE) — по data_nachala ASC, затем prioritet ASC,
                                     затем filial ASC, затем kod_raboty ASC
Внутри каждой работы: материалы по sys_nomer ASC
```

### Детали каждого слоя

**Слой 1 — Фактические списания**
- Источник: `_writeoff_cache[(work_id, material_id)]` — загружено в память в начале
- Одна строка `AllocationResult` на пару работа+материал
- `istochnik="spisanie"`, `warehouse_id=NULL`
- Склад **не меняется** (материал уже документально списан)

**Слой 2 — Выдано не списано**
- Источник: `_issued_cache[(work_id, material_id)]`
- `istochnik="vydano"`, склад **не меняется**

**Слой 3 — Склад (свой завод, потом свой филиал)**
- Подслои: `"zavod"` → `"filial"` (в порядке приоритета)
- FIFO внутри каждого подслоя
- Одна `AllocationResult` на каждый склад (WAC из накопителя)
- Одна `StockMovement` на каждую партию
- `_batch_cache[batch.id]` уменьшается; UPDATE в БД в конце

**Слой 3б — Возможное (другие филиалы)**
- Группа `"prochee"` из `get_available_by_warehouse_priority`
- `is_possible=True` — **не** уменьшает `remaining` и `dostupno`
- `istochnik="vozmozhnoe_sklad"` — только аналитика

**Слой 3в — Согласованные перемещения**
- Источник: `_approved_cache[(material_id, to_filial)]`
- Только если `self._approved_cache` не пустой (файл был загружен)
- Для каждого согласования: берём партии склада-источника (`from_warehouse_id`) FIFO
- `_batch_cache` и `_approved_qty_cache` уменьшаются
- `istochnik="odobren_perenos"`, `is_possible=False` — **реальное** распределение
- `remaining` уменьшается — потребность фактически закрывается

**Слой 4 — Поставки**
- Фильтр: `supply.filial == work.filial` (только своего филиала)
- Каждая строка поставки → отдельная `AllocationResult`
- `istochnik="postavka"`, `_supply_cache[line.id]` уменьшается

**Слой 5 — Дефицит**
- Если `remaining > EPSILON` после всех слоёв
- `estimated_cost = remaining × req.prognosnaya_tsena`

### Гарантии алгоритма

| Гарантия                        | Как реализовано                                             |
|---------------------------------|-------------------------------------------------------------|
| Нет отрицательных остатков      | `qty = min(remaining, available)`, порог EPSILON           |
| Нет двойного распределения      | `dostupno` уменьшается в кэше; повторный запрос — меньшее  |
| FIFO для партий                 | `ORDER BY data_postupleniya ASC` в SQL                     |
| WAC для склада                  | `_WarehouseAccumulator`: `weighted_cost_sum / total_qty`   |
| Поставки только своего филиала  | `WHERE supply.filial = work.filial`                        |
| Возможное не трогает остатки    | `is_possible=True`, кэши не меняются                       |
| Согласованные = реальные        | `is_possible=False`, `_batch_cache` уменьшается            |
| Завершённые работы не закупают  | `data_okonchaniya < сегодня` → только слои 1–2             |
| Повторный запуск — тот же итог  | `reset_dostupno()` перед каждым запуском                   |

## 8. Импорт данных — детальная схема

### Порядок загрузки

```
1. maps import-works        works.xlsx       ← даты и наименования работ
2. maps import-requirements requirements.xlsx ← СБРОС операционных данных + загрузка
3. maps import-emergency    emergency.xlsx   ← аварийные работы
4. maps import-stock        stock.xlsx       ← складские остатки (партии)
5. maps import-supplies     supplies.xlsx    ← поставки (материалы в пути)
6. maps import-writeoffs    writeoffs.xlsx   ← фактические списания (Слой 1)
7. maps import-issued       issued.xlsx      ← выдано не списано (Слой 2)
8. maps allocate                             ← первое распределение
   ↓ (анализ листа «Возможное перемещение»)
9. POST /api/import/transfers transfers.xlsx ← согласованные перемещения (Слой 3в)
10. maps allocate                            ← повторное распределение
```

### Что происходит при `import-requirements`

1. Удаляет: `StockMovement → AllocationResult → DeficitRecord → AllocationSession →
   WriteOff → IssuedNotWrittenOff → SupplyLine → Supply → StockBatch → Requirement`
2. `works` — **не удаляет** (мастер-данные сохраняются)
3. `approved_transfers` — **не удаляет** (загружаются отдельно)
4. Загружает словари `{kod_raboty: id}` и `{sys_nomer: id}` в память
5. Для каждой строки: валидация → `get_or_create Work` → `get_or_create Material` → `upsert Requirement`

### Формат входных файлов

Все файлы принимаются в **русском формате**:
- Даты: `ДД.ММ.ГГГГ` (например `28.05.2026`). ISO-формат `2026-05-28` тоже поддерживается.
- Числа: разделитель дробной части — **запятая** (`1234,56`), тысячи — пробел (`1 234,56`).
- Пустые ячейки: трактуются как `0` для числовых полей, `""` для строковых.

## 9. Экспорт — структура отчёта (до 11 листов)

| № | Лист | Функция | Откуда данные | Ключевая логика |
|---|---|---|---|---|
| 1 | Распределение | `_get_wide_allocation_df` | requirements + allocation_results | pivot-like через pandas merge |
| 2 | Движение склада | `_get_movement_df` | stock_movements | JOIN с work, warehouse, material |
| 3 | Остатки складов после распределения | `_get_warehouse_balances_df` | stock_batches | kolichestvo → распределено → dostupno |
| 4 | Возможное перемещение | `_get_possible_movements_df` | allocation_results WHERE is_possible | аналитика |
| 5 | Одобренные перемещения | `_get_approved_transfers_df` | allocation_results WHERE odobren_perenos | условный лист |
| 6 | Обеспеченность | `_get_coverage_by_work_df` | requirements + allocation_results | GROUP BY work |
| 7 | В пути | `_get_in_transit_allocated_df` | supply_lines + allocation_results | зарезервированные поставки |
| 8 | Не распред. в пути | `_get_in_transit_unallocated_df` | supply_lines WHERE dostupno > 0 | свободные объёмы |
| 9 | Исх. Потребности | `_get_source_requirements_df` | requirements JOIN works, materials | исходные данные для аудита |
| 10 | Исх. Остатки складов | `_get_source_stock_df` | stock_batches JOIN warehouses, materials | начальные остатки |
| 11 | Исх. Поставки | `_get_source_supplies_df` | supply_lines JOIN supplies, materials | все строки поставок |

> Лист 5 «Одобренные перемещения» добавляется только если в этой сессии были
> использованы согласованные перемещения (`df_approved.empty == False`).

**Формула % обеспечённости (по стоимости):**
```
covered = sp_summa + vd_summa + sk_summa + od_summa + pv_summa
total    = potrebnost × prognosnaya_tsena
coverage = covered / total × 100
```
Если `prognosnaya_tsena = 0` — обеспечённость по количеству: `raspredeleno / potrebnost × 100`.

**Формат чисел и дат в отчёте:**
- Числа: `"1234,56"` (запятая) — гарантирует корректный вид в Excel с русской локалью
- Даты: `"28.05.2026"` (ДД.ММ.ГГГГ)

## 12. AI-функциональность

### `deficit_analyzer.py` — объяснение дефицита

Извлекает из БД детали по конкретному материалу и вызывает Claude API:
- Какие работы в дефиците и сколько им нужно
- Что дал каждый слой (Слой 1–4, 3в)
- Текущие складские остатки по филиалам
- Ближайшие поставки

Claude (model `claude-opus-4-7`) отвечает на русском: объясняет причину дефицита
и даёт рекомендации.

### `session_rag.py` — RAG-чат

RAG (Retrieval-Augmented Generation): перед вызовом Claude извлекаются
дефицитные материалы, остатки, поставки — добавляются в контекст запроса.

## 18. Как запустить локально

```bash
# 1. Клонировать
git clone https://github.com/DaniarSher81212/maps.git
cd maps

# 2. Установить зависимости
pip install -e ".[dev]"

# 3. Создать .env
cp .env.example .env
# отредактировать: DB_PASSWORD, ANTHROPIC_API_KEY (опционально)

# 4. Создать таблицы
maps init
# или через Alembic: alembic upgrade head

# 5. Загрузить данные (порядок важен)
maps import-works        data/sample_works.xlsx
maps import-requirements data/sample_requirements.xlsx
maps import-stock        data/sample_stock.xlsx
maps import-supplies     data/sample_supplies.xlsx
maps import-writeoffs    data/sample_writeoffs.xlsx
maps import-issued       data/sample_issued.xlsx

# 6. Запустить распределение
maps allocate

# 7. Экспортировать отчёт
maps export
# Файл в data/exports/

# 8. ИЛИ запустить веб-сервер
maps serve
# Дашборд: http://localhost:8000
# Swagger:  http://localhost:8000/docs
```
