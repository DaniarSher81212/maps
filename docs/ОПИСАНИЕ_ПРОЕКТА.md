## 1. Что такое MAPS и зачем он нужен

MAPS — система автоматического распределения строительных материалов.

### Бизнес-задача

На предприятии одновременно ведутся сотни строительно-монтажных работ (СМР).
У каждой работы есть список нужных материалов с количествами — это **потребность**.

Материалы хранятся:
- **На складах** — конкретные партии с ценой и датой поступления
- **В поставках** — заказаны у поставщиков, ещё едут («в пути»)
- **Уже списаны** — оформлены документально на работу в SAP (система учёта)
- **Выданы, но не списаны** — физически на объекте, документ ещё не оформлен

**Проблема без MAPS:** плановый отдел вручную в Excel разбирает: кому дать какой материал.
Это часами, с ошибками, непрозрачно.

**Решение MAPS:** 5-слойный алгоритм автоматически закрывает потребности работ,
соблюдая приоритет (аварийные → по дате → плановые), и выдаёт Excel-отчёт с
процентом обеспечённости и списком «К закупу».

### 4.1 `app/core/config.py` — Конфигурация

**Назначение:** Единое место для всех настроек приложения. Читает переменные из файла `.env`.

### 4.2 `app/db/database.py` — Подключение к PostgreSQL

**Назначение:** Создаёт соединение с PostgreSQL и управляет транзакциями.

**Три ключевых объекта:**

**1) `engine` — движок (пул соединений)**
```python
engine = create_engine(
    settings.db_url,
    pool_size=5,         # 5 постоянных соединений
    max_overflow=10,     # ещё до 10 временных при пике
    pool_pre_ping=True,  # проверять соединение перед использованием
    echo=settings.is_development,  # выводить SQL в лог при разработке
)
```
Пул соединений нужен для производительности: открытие нового TCP-соединения к PostgreSQL
занимает ~20 мс. Без пула при 100 запросах/сек — 2 секунды только на установку соединений.

**2) `SessionLocal` — фабрика сессий**
```python
SessionLocal = sessionmaker(
    bind=engine,
    autocommit=False,  # изменения только при явном commit()
    autoflush=False,   # не отправлять SQL до commit()
)
```
`autoflush=False` важно! При `True` SQLAlchemy сам вставляет flush перед каждым SELECT,
что может вызвать неожиданные INSERT в середине транзакции.

**3) `get_session()` — контекстный менеджер**
```python
@contextmanager
def get_session() -> Generator[Session, None, None]:
    session = SessionLocal()
    try:
        yield session      # отдаём сессию в блок with
        session.commit()   # успех → сохраняем всё
    except Exception:
        session.rollback() # ошибка → откатываем всё
        raise
    finally:
        session.close()    # всегда закрываем (возвращаем в пул)
```

**Использование везде в коде:**
```python
with get_session() as session:
    work = session.get(Work, work_id)
    session.add(new_work)
    # commit автоматически при выходе из with
```

**Почему не используем FastAPI Depends для БД?**
Некоторые операции (импорт, распределение) запускаются из CLI или фонового задания,
где нет HTTP-запроса и нет FastAPI Depends. `get_session()` работает везде.

### 4.3 `app/db/models.py` — ORM-модели (таблицы БД)

**Назначение:** Каждый класс = одна таблица в PostgreSQL. Каждый атрибут = колонка.

**Почему SQLAlchemy 2.x `Mapped[тип]`?**
Современный синтаксис даёт IDE-автодополнение и проверку типов:
```python
# Старый синтаксис (SQLAlchemy 1.x):
kod_raboty = Column(String(100), nullable=False)

# Новый синтаксис (SQLAlchemy 2.x):
kod_raboty: Mapped[str] = mapped_column(String(100), nullable=False)
# IDE знает, что work.kod_raboty — это str, не Any
```

**Ключевые поля и почему они именно такие:**

`Work.is_emergency` — булево поле. Аварийные работы идут перед всеми обычными.
`Work.data_nachala` — ГЛАВНЫЙ критерий сортировки (не `prioritet`!). Кто начинается раньше — тот и первый.
`Work.prioritet` — дополнительный для ОБЫЧНЫХ работ, игнорируется у аварийных.
`Requirement.prognosnaya_tsena` — прогнозная цена из заявки. Нужна для расчёта % обеспечённости по стоимости и стоимости «К закупу».
`Requirement.raspredeleno` — заполняется алгоритмом. Накапливается в памяти, потом пишется в БД.
`StockBatch.dostupno` — текущий доступный остаток (меньше или равен `kolichestvo`). Уменьшается алгоритмом.
`StockBatch.data_postupleniya` — для FIFO-сортировки: старые партии расходуются первыми.
`Supply.filial` — КЛЮЧЕВОЕ ПОЛЕ. Поставки привязаны к филиалу, не к заводу.
`AllocationResult.is_possible` — `True` = анализ («возможное»), `False` = факт. Только `is_possible=False` меняет остатки.
`AllocationResult.istochnik` — код источника: `"spisanie"` / `"vydano"` / `"sklad"` / `"vozmozhnoe_sklad"` / `"postavka"`.

**Индексы в БД:**
```python
__table_args__ = (
    Index("ix_requirements_work_material", "work_id", "material_id", unique=True),
)
```
Индексы ускоряют поиск. `unique=True` гарантирует: одна пара «работа + материал» = одна строка потребности.

### 4.4 `app/models/schemas.py` — Pydantic-схемы для валидации

**Назначение:** Проверяет каждую строку Excel перед записью в БД.
Если данные некорректны — понятное сообщение об ошибке, строка пропускается.

**Чем отличается от ORM-моделей?**
```
ORM (models.py)   → описывает ТАБЛИЦЫ в PostgreSQL
Pydantic (schemas.py) → описывает ДАННЫЕ при вводе (Excel-строки, API-запросы)
```
ORM знает про первичные ключи, FK, индексы.
Pydantic знает про бизнес-правила: количество > 0, дата начала ≤ дате окончания.

**Почему `Decimal`, а не `float`?**
```python
# float — ошибка округления:
>>> 0.1 + 0.2
0.30000000000000004

# Decimal — точность:
>>> Decimal("0.1") + Decimal("0.2")
Decimal("0.3")
```
В финансовых расчётах (стоимости, количества) это критично!

**`field_validator` — нормализация Excel-данных:**
```python
@field_validator("kod_raboty", mode="before")
@classmethod
def strip_and_upper(cls, v):
    s = str(v).strip()
    if s.endswith(".0"):
        s = s[:-2]  # "WO12345.0" → "WO12345" (Excel форматирует как float)
    return s
```
Excel часто форматирует числовые коды как `10012345.0` — нужно убирать `.0`.

**`model_validator` — проверка связанных полей:**
```python
@model_validator(mode="after")
def check_dates(self):
    if self.data_nachala and self.data_okonchaniya:
        if self.data_nachala > self.data_okonchaniya:
            raise ValueError("Дата начала не может быть позже даты окончания")
    return self
```
Это бизнес-правило: логика дат — не `field_validator` (он видит одно поле),
а `model_validator` (видит все поля вместе).

**Схемы импорта:**
- `WorkImportRow` — строка файла потребностей (обычные и аварийные работы)
- `WorkListImportRow` — строка файла «Перечень работ» (только мастер-данные: наименование, даты)
- `StockImportRow` — строка файла складских остатков
- `SupplyImportRow` — строка файла поставок
- `WriteOffImportRow` — строка файла фактических списаний
- `IssuedNotWrittenOffImportRow` — строка файла «Выдано не списано»

### 4.5 `app/repositories/base.py` — Базовый репозиторий

**Назначение:** Паттерн Repository — изолирует SQL-запросы от бизнес-логики.

**Что такое паттерн Repository?**
```python
# БЕЗ паттерна (плохо — SQL прямо в бизнес-логике):
def allocate(session, work_id):
    work = session.query(Work).filter(Work.id == work_id).first()
    materials = session.query(Material).join(Requirement)...

# С ПАТТЕРНОМ (хорошо — логика работает с объектами):
def allocate(work_repo, material_repo):
    work = work_repo.get_by_id(work_id)
    materials = material_repo.get_for_work(work_id)
```

**Generic[T] — универсальный класс:**
```python
T = TypeVar("T", bound=Base)

class BaseRepository(Generic[T]):
    # Один класс работает с любой ORM-моделью:
    # WorkRepository(session, Work)
    # MaterialRepository(session, Material)
```

**CRUD-методы:**
- `get_by_id(id)` — SELECT по первичному ключу
- `get_all()` — SELECT * (осторожно с большими таблицами!)
- `add(obj)` — добавить в сессию (не в БД, нужен commit)
- `add_all(list)` — массовая вставка
- `delete(obj)` — удалить
- `flush()` — отправить изменения в БД без коммита (нужен для получения ID)
- `count()` — COUNT(*)

### 4.6 `app/repositories/material_repository.py` — Репозитории материалов и слоёв 1–2

Содержит **5 репозиториев**:

#### `MaterialRepository`

`get_or_create(sys_nomer, naimenovanie, ...)` — главный метод.
Материалы встречаются в разных Excel-файлах. Если уже есть — не дублируем.
Если пришли с новым наименованием — обновляем (только если поле было пустым).

`get_id_map()` — возвращает `{sys_nomer: id}` для **быстрого поиска при импорте**.
Без этого метода: импорт 10 000 строк = 10 000 SELECT-запросов (медленно).
С этим методом: один SELECT, потом поиск в словаре за O(1).

#### `StockBatchRepository`

`get_available_by_warehouse_priority(material_id, zavod, filial)` — ключевой метод для слоя 3.
Возвращает партии, разбитые на три группы:
```python
{
    "zavod":   [...],  # тот же завод — высший приоритет
    "filial":  [...],  # тот же филиал — средний
    "prochee": [...],  # другие филиалы — только для анализа
}
```
Разделение на Python (не SQL) — один запрос к БД, потом быстрая группировка в памяти.

`reset_dostupno()` — восстанавливает `dostupno = kolichestvo` у всех партий.
Вызывается перед каждым запуском алгоритма. Зачем? Алгоритм уменьшает `dostupno`
и сохраняет в БД. При повторном запуске нужно начать с «полным складом».

#### `SupplyRepository`

`get_available_lines_for_material(material_id, filial)` — возвращает строки поставок.
**Ключевое бизнес-правило:** фильтруем по `filial` поставки = `filial` работы.
Поставки идут на ФИЛИАЛ, не на конкретный завод.

`reset_dostupno()` — то же что у StockBatch, но для строк поставок.

#### `WriteOffRepository`

`get_all_grouped_by_work_material()` — загружает ВСЕ списания одним SELECT
и группирует в словарь `{(work_id, material_id): [WriteOff, ...]}`.

**Зачем грузить всё сразу?** Алгоритм обрабатывает тысячи потребностей.
Если делать SELECT для каждой — N+1 запросов. Один SELECT + словарь в памяти — быстрее в 100 раз.

#### `IssuedNotWrittenOffRepository`

Аналогично `WriteOffRepository`, но для слоя 2 («Выдано не списано»).

### 4.7 `app/repositories/work_repository.py` — Репозиторий работ и потребностей

#### `WorkRepository`

`get_or_create(kod_raboty, ...)` — создаёт или возвращает работу.
Параметр `is_emergency=True` используется при импорте аварийных работ:
если работа уже есть — просто обновляет флаг `is_emergency`.

`get_active_sorted()` — работы в правильном порядке распределения.
Использует SQL `CASE`:
```sql
CASE WHEN NOT is_emergency THEN prioritet ELSE 0 END ASC
```
Для аварийных работ `prioritet` игнорируется (они уже выше по `is_emergency DESC`).

`get_kod_map()` — `{kod_raboty: id}` для быстрого поиска при импорте (O(1)).

#### `RequirementRepository`

`upsert(work_id, material_id, potrebnost, prognosnaya_tsena)` — создаёт или суммирует.
**Почему суммируем, а не заменяем?**
В Excel один материал может встречаться в нескольких строках для одной работы
(разные подрядчики, разные секции объекта). Бизнес-правило: суммируем.

`get_for_allocation()` — ГЛАВНЫЙ запрос алгоритма.
Возвращает `[(Requirement, Work, Material), ...]` в порядке распределения:
```sql
ORDER BY
    works.is_emergency DESC,              -- 1. Аварийные первыми
    works.data_nachala ASC NULLS LAST,    -- 2. По дате (ГЛАВНЫЙ критерий)
    CASE WHEN NOT is_emergency THEN prioritet ELSE 0 END ASC,  -- 3. Приоритет
    works.filial ASC,                     -- 4. Филиал
    works.kod_raboty ASC,                 -- 5. Код работы
    materials.sys_nomer ASC               -- 6. Материал
```

`reset_allocation()` — обнуляет `raspredeleno = 0` и `deficit = 0` у всех потребностей.
Вызывается в начале каждого запуска. Без сброса — повторный запуск накапливал бы значения.

### 4.8 `app/services/import_service.py` — Импорт из Excel

**Назначение:** Читает Excel-файлы и записывает данные в PostgreSQL.
Один файл содержит **7 функций импорта** для 6 типов файлов + перечень работ.

**Общий принцип работы:**
```
Excel → pandas (dtype=str) → _rename_columns(column_map)
     → for row: Pydantic.validate()
     → get_or_create / upsert
     → session.flush() периодически
     → session.commit() при выходе из get_session()
```

**Почему `dtype=str` в pandas?**
```python
df = pd.read_excel(file_path, dtype=str, keep_default_na=False)
```
Без `dtype=str` pandas сам угадывает типы:
- `"10012345"` → `10012345.0` (float!) — ломает SAP-номера
- `"2026-01-15"` → `Timestamp(...)` — сложно передать в Pydantic
- Пустые ячейки → `NaN` — вызывают ошибки в `str.strip()`

`keep_default_na=False` — пустые ячейки остаются пустыми строками `""`, не `NaN`.

**`column_map` — маппинг колонок Excel → поля схемы:**
```python
REQUIREMENTS_COLUMN_MAP = {
    "Код работы":      "kod_raboty",
    "Системный номер": "sys_nomer_materiala",
    "Потребность":     "potrebnost",
    ...
}
```
Если клиент изменит заголовки Excel — меняем только этот словарь, а не логику.

**`_get_or_create_warehouse(session, ...)` — создаёт склад если нет:**
Склады не приходят отдельным файлом — они создаются автоматически при импорте
остатков и поставок, по коду склада (`kod_sklada`).

#### `import_requirements()` — главный импорт потребностей

**Что делает:**
1. Полный сброс операционных данных (кроме таблицы `works`)
2. Предзагрузка словарей `{kod_raboty: id}` и `{sys_nomer: id}`
3. Для каждой строки: валидация → get_or_create Work → get_or_create Material → upsert Requirement

**Почему `works` НЕ очищается:**
Таблица `works` — это мастер-данные. Если загрузить «Перечень работ» (`import-works`)
с наименованиями и датами, а потом загрузить потребности — даты должны сохраниться.
Очистка `works` уничтожила бы их. `get_or_create` предотвращает дубли.

**Двойной flush (технический долг):**
```python
if stats["requirements"] % 500 == 0:
    session.flush()      # периодический
session.flush()          # ← на каждой строке (лишний!)
```
Второй `flush()` на каждой строке — медленно при больших файлах. Нужно убрать.

#### `import_emergency_works()` — аварийные работы

Формат файла **такой же**, как обычные потребности (тот же `REQUIREMENTS_COLUMN_MAP`).
Единственное отличие: `is_emergency=True` при создании работ.
Перед импортом удаляет только аварийные работы (не все).

#### `import_stock()` — складские остатки

**Полная замена:** удаляет все старые партии и загружает заново («снимок склада»).
`dostupno = kolichestvo` при создании — весь объём изначально доступен.

#### `import_supplies()` — поставки

Группировка строк Excel по `dogovor_key`:
```python
dogovor_key = f"{dogovor}_{kod_sklada}_{data_postavki}"
```
Несколько строк одного договора → один `Supply` + несколько `SupplyLine`.

#### `import_writeoffs()` — фактические списания

**Важно:** если работа не найдена — строка пропускается.
Сначала нужно загрузить потребности (`import-requirements`).
Если материал не найден — создаётся автоматически.

#### `import_issued_not_written_off()` — выдано не списано

Аналогично `import_writeoffs()`. Поле `warehouse_id` — только информативное,
алгоритм при обработке этого слоя **не изменяет остатки склада**.

#### `import_works()` — перечень работ (мастер-данные)

**Upsert без очистки:** обновляет существующие работы, создаёт новые.
Обновляет только непустые поля:
```python
if validated.nazvanie:
    work.nazvanie = validated.nazvanie  # обновляем только если в файле есть значение
if validated.prioritet != 3:
    work.prioritet = validated.prioritet  # не затираем реальный приоритет дефолтом
```
Это защита: если в файле не заполнено поле — существующие данные не затираются.

### 4.9 `app/allocation/engine.py` — Ядро: алгоритм распределения

**Это самый важный файл проекта.** Класс `AllocationEngine` реализует 5-слойный алгоритм.

#### Вспомогательный класс `_WarehouseAccumulator`

**Проблема:** один склад может иметь несколько партий с разными ценами.
В отчёте нужна **одна строка на склад** со **средней взвешенной ценой (WAC)**.

```
Склад W-001:
  Партия 001: 100 м × 1500 тг/м = 150 000 тг
  Партия 002:  50 м × 1600 тг/м =  80 000 тг
  ─────────────────────────────────────────────
  Итого:      150 м × 1533 тг/м = 230 000 тг  ← это WAC
```

**Как считается WAC:**
```python
avg_cost = weighted_cost_sum / total_qty
# = (100×1500 + 50×1600) / (100 + 50) = 230000 / 150 = 1533.33
```

Накопитель собирает партии через `acc.add(qty, cost)`, потом создаётся одна строка результата.

#### `EPSILON = Decimal("0.0001")`

Минимальное значимое количество. Всё что меньше считается нулём.
Нужно чтобы не распределять «5e-7 метров кабеля» из-за ошибок округления Decimal.

#### Класс `AllocationEngine.__init__`

Инициализирует:
- **Репозитории** — доступ к БД (5 штук)
- **Буферы** — списки объектов для batch-INSERT в конце (`_allocation_buffer`, `_movement_buffer`, `_deficit_buffer`)
- **Кэши** — словари для текущих остатков в памяти (`_batch_cache`, `_supply_cache`)
- **Кэши слоёв 1 и 2** — предзагруженные данные списаний и выданного
- **Статистика** — счётчики для итогового отчёта

**Зачем буферы и кэши?**
При 5000 потребностях построчный INSERT = 5000 запросов к БД.
`bulk_save_objects()` в конце = 1 запрос. В 10–50 раз быстрее.

#### `AllocationEngine.run()` — точка входа

**8 шагов:**
```
1. Создать запись AllocationSession (статус "running")
2. Загрузить слои 1 и 2 в память (WriteOff, IssuedNotWrittenOff)
3. Сбросить предыдущие результаты (raspredeleno=0, dostupno=kolichestvo)
4. Получить все потребности в порядке распределения
5. Для каждой потребности: _process_requirement()
6. batch-INSERT накопленных результатов
7. UPDATE остатков партий и поставок в БД
8. Обновить сессию: статус "completed", статистика
```

Если шаги 5–8 падают с ошибкой — сессия помечается `"failed"`, ошибка пробрасывается.

#### `_process_requirement(req, work, material)` — обработка одной потребности

**Входящий параметр `remaining`:**
```python
remaining = req.potrebnost - req.raspredeleno
```
Начинается с полной непокрытой потребности. Каждый слой уменьшает его.

**Завершённые работы** (`data_okonchaniya < сегодня`):
Обрабатываются только слои 1 и 2. Закупать для завершённой работы нет смысла.
Склад и поставки — для будущих работ.

**5 слоёв в порядке обработки:**
```
remaining = potrebnost
    ↓ Слой 1: фактические списания (WriteOff)
remaining -= qty_writeoff
    ↓ Слой 2: выдано не списано (IssuedNotWrittenOff)
remaining -= qty_issued
    ↓ Слой 3: склад (свой завод → свой филиал, FIFO)
remaining -= qty_warehouse
    │ Слой 3б: другие филиалы (is_possible=True, remaining НЕ меняется)
    ↓ Слой 4: поставки своего филиала
remaining -= qty_supply
    ↓ Слой 5: дефицит (К закупу) = оставшееся remaining
```

#### `_apply_writeoff_layer` — слой 1

```python
key = (work.id, material.id)
writeoffs = self._writeoff_cache.get(key, [])  # O(1) из памяти, не из БД
total_qty = sum(wo.kolichestvo for wo in writeoffs)
qty = min(remaining, total_qty)  # не больше потребности!
```

Создаётся **одна** строка `AllocationResult` с `istochnik="spisanie"` — агрегированно.
`warehouse_id=None` — материал уже списан, к складу не привязан.

#### `_apply_issued_layer` — слой 2

Аналогично слою 1, но `istochnik="vydano"`.
Остатки склада **не меняем** — материал уже физически ушёл со склада.

#### `_allocate_from_warehouse` — слой 3

Использует `get_available_by_warehouse_priority` → получает три группы партий.
Обрабатывает только `"zavod"` и `"filial"`, пропуская `"prochee"`.

**Внутри каждой группы:**
1. FIFO — партии уже отсортированы по `data_postupleniya`
2. Для каждой партии: берём `min(remaining, batch.dostupno)`
3. Обновляем `_batch_cache[batch.id]` (НЕ БД — кэш в памяти)
4. Создаём `StockMovement` — детальная запись движения по партии
5. Добавляем в `_WarehouseAccumulator` для этого склада

После всех партий группы создаётся **одна** строка `AllocationResult` на каждый склад
(с `avg_cost` из накопителя).

#### `_record_possible_from_other_filial` — слой 3б

Берёт группу `"prochee"` (другие филиалы).
`is_possible=True` — не меняет `remaining`, не уменьшает остатки.
Использует `batch.dostupno` напрямую (не из `_batch_cache` — чужой склад не тронут).

#### `_allocate_from_supplies` — слой 4

Фильтрует по `filial=work.filial` — бизнес-правило.
Каждая строка поставки → отдельная строка `AllocationResult` с `istochnik="postavka"`.
Уменьшает `_supply_cache[line.id]`.

#### `_record_deficit` — слой 5

```python
estimated_cost = deficit_qty × req.prognosnaya_tsena
```
Стоимость «К закупу» считается по прогнозной цене из заявки.

#### `_flush_buffers_to_db` — batch-INSERT

```python
self.session.bulk_save_objects(self._allocation_buffer)  # все результаты одним INSERT
self.session.bulk_save_objects(self._movement_buffer)    # все движения
self.session.bulk_save_objects(self._deficit_buffer)     # все дефициты
self.session.flush()
```

#### `_update_availability_in_db` — обновление остатков

```python
for batch_id, new_available in self._batch_cache.items():
    batch = self.session.get(StockBatch, batch_id)
    batch.dostupno = new_available   # UPDATE только изменённых партий
```
Обновляем только те партии и строки поставок, которые были задействованы.

### 4.10 `app/services/export_service.py` — Экспорт в Excel

**Назначение:** Формирует многолистовой Excel-отчёт из данных PostgreSQL.

**Функция `export_allocation_results(session_id)`** — точка входа.
Открывает одну сессию БД, выполняет 7 SQL-запросов, пишет 7 листов.

**Почему pandas, а не openpyxl напрямую?**
pandas умеет агрегировать данные (groupby, merge, pivot-like операции).
openpyxl — низкоуровневая работа с ячейками, без агрегации.
Связка pandas + openpyxl: pandas строит DataFrame → openpyxl записывает в файл.

#### Лист 1: «Распределение» — главная широкая таблица

Подход: **разворачиваем слои в колонки** (pivot-like без SQL PIVOT):
```
requirement_id | sp_qty | sp_price | vd_qty | sk_qty | sk_price | pv_qty | zakup_qty | pct
─────────────────────────────────────────────────────────────────────────────────────────
R-001          | 60     | 1500     | 10     | 30     | 1533     | 0      | 0         | 100%
R-002          | 0      | 0        | 0      | 50     | 1450     | 20     | 30        | 56%
```

Алгоритм построения:
```
1. SELECT все потребности (с данными работы и материала)
2. SELECT все строки распределения (WHERE is_possible=FALSE)
3. Группируем в Python по (requirement_id, istochnik)
4. _agg_layer("spisanie")  → df_sp (qty, summa, avg_price)
5. _agg_layer("vydano")    → df_vd
6. _agg_layer("sklad")     → df_sk
7. _agg_layer("postavka")  → df_pv (+ договора, поставщики через ", ".join)
8. LEFT JOIN через pandas.merge: потребности ← слои
9. Рассчитываем: prognosnaya_stoimost, k_zakupu_summa, coverage_pct
```

**Формула обеспечённости (по стоимости, не по количеству):**
```python
covered_cost = sp_summa + vd_summa + sk_summa + pv_summa
total_cost   = potrebnost × prognosnaya_tsena
coverage_pct = covered_cost / total_cost × 100
```
Если `prognosnaya_tsena = 0` — обеспечённость считается по количеству.

#### Лист 2: «Движение склада»

Детальные движения по партиям: склад → партия → работа → материал → Δ количество → остаток.
Одна строка = одно списание одной партии на одну работу.

#### Лист 3: «Остатки складов»

Агрегированные остатки: начальный `kolichestvo` → распределено → `dostupno`.

#### Лист 4: «Возможное перемещение»

Результаты `is_possible=TRUE` — что можно перебросить из других филиалов.

#### Лист 5: «Обеспеченность»

Сводка по работам: потребность, покрыто, дефицит, % обеспечённости.

#### Листы 6–7: «В пути» и «Не распред. в пути»

«В пути» — поставки, зарезервированные под работы (есть строки распределения).
«Не распред. в пути» — поставки, у которых `dostupno > 0` после распределения (свободные объёмы).

### 4.17 `app/ai/deficit_analyzer.py` — AI-объяснение дефицита

### 4.18 `main.py` — CLI-команды (Typer)

**Назначение:** Все команды `maps ...` для работы из терминала.
**Typer** = современная замена `argparse`, использует Python-аннотации для описания аргументов.

## 7. Алгоритм распределения (5 слоёв) — детально

### Порядок работ

```
1. Аварийные (is_emergency=TRUE) — по data_nachala ASC NULLS LAST
2. Обычные (is_emergency=FALSE)  — по data_nachala ASC, затем prioritet ASC,
                                   затем filial ASC, затем kod_raboty ASC
```

Внутри каждой работы — её потребности по `materials.sys_nomer ASC`.

### Детали каждого слоя

**Слой 1 — Фактические списания (`WriteOff`)**
- Источник: `_writeoff_cache[(work_id, material_id)]`
- Агрегированно: одна строка результата на пару работа+материал
- `istochnik = "spisanie"`, `warehouse_id = NULL`
- Склад НЕ меняется (материал уже списан)

**Слой 2 — Выдано не списано (`IssuedNotWrittenOff`)**
- Источник: `_issued_cache[(work_id, material_id)]`
- Аналогично слою 1
- `istochnik = "vydano"`
- Склад НЕ меняется (материал уже ушёл физически)

**Слой 3 — Склад (фактическое)**
- Два подслоя: `"zavod"` (приоритет 1) и `"filial"` (приоритет 2)
- FIFO внутри каждого подслоя
- Для каждого склада — один `_WarehouseAccumulator` → одна строка результата (WAC)
- Для каждой партии — одна `StockMovement` (детальное движение)
- `istochnik = "sklad"`, `tip_raspredeleniya = "zavod"` или `"filial"`
- `_batch_cache[batch.id]` уменьшается — UPDATE в БД в конце

**Слой 3б — Возможное (другие филиалы)**
- Группа `"prochee"` из `get_available_by_warehouse_priority`
- `is_possible = True` — НЕ уменьшает `remaining` и `dostupno`
- `istochnik = "vozmozhnoe_sklad"`, `tip_raspredeleniya = "vozmozhnoe"`
- Показывает сколько МОЖНО было взять при согласовании переброски

**Слой 4 — Поставки (`SupplyLine`)**
- Фильтр: `supply.filial == work.filial` (только своего филиала!)
- Сортировка: ближайшие даты поставки — первые
- Каждая строка поставки → отдельная строка результата (`istochnik = "postavka"`)
- `_supply_cache[line.id]` уменьшается

**Слой 5 — Дефицит**
- Если `remaining > EPSILON` после всех слоёв
- `estimated_cost = remaining × req.prognosnaya_tsena`
- Запись в `DeficitRecord`

### Гарантии алгоритма

| Гарантия                  | Как реализовано                                          |
|---------------------------|----------------------------------------------------------|
| Нет отрицательных остатков | `qty = min(remaining, available)`, EPSILON-порог        |
| Нет двойного распределения | `dostupno` уменьшается, повторный запрос видит меньшее  |
| FIFO                       | ORDER BY `data_postupleniya ASC` в SQL                  |
| WAC для склада             | `_WarehouseAccumulator.weighted_cost_sum / total_qty`   |
| Поставки только своего филиала | `WHERE supply.filial = work.filial`                 |
| Возможное не трогает остатки | `is_possible=True`, `dostupno` не меняется             |

## 8. Импорт данных — детальная схема

### Порядок загрузки (рекомендуемый)

```
maps import-works requirements.xlsx        ← даты и наименования работ (можно после)
maps import-requirements requirements.xlsx ← СБРОС всех данных (кроме works) + загрузка
maps import-emergency emergency.xlsx       ← добавляет аварийные работы
maps import-stock stock.xlsx               ← складские остатки (партии)
maps import-supplies supplies.xlsx         ← поставки (материалы в пути)
maps import-writeoffs writeoffs.xlsx       ← фактические списания (Слой 1)
maps import-issued issued.xlsx             ← выдано не списано (Слой 2)
maps allocate                              ← запуск распределения
maps export                                ← Excel-отчёт
```

### Что происходит при `import-requirements`

1. Удаляет: `StockMovement → AllocationResult → DeficitRecord → AllocationSession → WriteOff → IssuedNotWrittenOff → SupplyLine → Supply → StockBatch → Requirement`
2. `works` НЕ удаляет — мастер-данные сохраняются
3. Загружает словари в память: `{kod_raboty: id}` и `{sys_nomer: id}` — O(1) поиск
4. Для каждой строки Excel: валидация → создание работы → создания материала → upsert потребности

### Что происходит при `import-works`

- Только upsert в таблицу `works`
- Обновляет поля если они непустые в файле
- Не затрагивает другие таблицы
- Можно запускать до или после `import-requirements`

## 9. Экспорт — 7 листов отчёта

| Лист                      | Откуда данные                          | Ключевая логика                        |
|---------------------------|----------------------------------------|----------------------------------------|
| **Распределение**         | requirements + allocation_results      | pivot-like через pandas merge          |
| **Движение склада**       | stock_movements                        | прямой SELECT с JOIN                   |
| **Остатки складов**       | stock_batches                          | kolichestvo, распределено, dostupno    |

| **Обеспеченность**        | requirements + allocation_results      | GROUP BY work, сводка                  |
| **В пути**                | supply_lines + allocation_results      | зарезервированные поставки             |
| **Не распред. в пути**    | supply_lines WHERE dostupno > 0        | свободные поставки после распределения |

**Формула % обеспечённости:**
```
Если prognosnaya_tsena > 0:
    coverage = (sp_summa + vd_summa + sk_summa + pv_summa) / (potrebnost × tsena) × 100
Иначе (по количеству):
    coverage = raspredeleno / potrebnost × 100
```

## 18. Как запустить локально

```bash
# 1. Клонировать
git clone https://github.com/DaniarSher81212/maps.git
cd maps

# 2. Установить зависимости
pip install -e ".[dev]"

# 3. Создать .env
cp .env.example .env
# отредактировать: DB_PASSWORD, ANTHROPIC_API_KEY (опционально)

# 4. Создать таблицы
maps init

# 5. Загрузить тестовые данные (в порядке)
maps import-works      data/sample_works.xlsx
maps import-requirements data/sample_requirements.xlsx
maps import-stock      data/sample_stock.xlsx
maps import-supplies   data/sample_supplies.xlsx

# 6. Запустить распределение
maps allocate

# 7. Экспортировать отчёт
maps export
# Файл будет в data/exports/

# 8. ИЛИ запустить веб-сервер
maps serve
# Открыть http://localhost:8000
# Swagger: http://localhost:8000/docs
```
