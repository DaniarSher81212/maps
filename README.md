## 1. Что делает система

MAPS решает задачу: **кому и откуда дать материалы при ограниченных ресурсах**.

Представьте ситуацию:
- 500 строительных работ требуют материалы
- Часть материалов уже **списана** на конкретные работы в SAP
- Часть **выдана физически**, но ещё не списана документально
- На складах есть партии разных дат и цен
- Часть материалов ещё «в пути» (подтверждённые поставки)
- Некоторых материалов не хватает (дефицит — к закупу)
- Некоторые работы — **аварийные** и требуют немедленного обеспечения
- Работы имеют разные приоритеты и сроки начала

Вручную это решить за разумное время невозможно. MAPS автоматически:

| Задача | Результат |
|--------|-----------|
| Анализирует списания (WriteOff) из SAP | Сколько уже «закрыто» документально |
| Анализирует выданное не списанное | Сколько фактически на руках у рабочих |
| Ищет материалы на складах своего филиала | Соблюдает FIFO и приоритеты |
| Резервирует из поставок своего филиала | Если склада не хватает |
| Фиксирует дефицит (к закупу) | Список позиций с оценочной стоимостью |
| Рассчитывает обеспечённость по стоимости | % покрытия = закрытая стоимость / (потребность × прогнозная цена) |
| Показывает возможные перемещения | Склады других филиалов, откуда можно привезти |

## 2. Как работает алгоритм — 5 слоёв

Для каждой потребности (работа + материал + количество) алгоритм последовательно проходит 5 слоёв. Следующий слой активируется только если предыдущий не закрыл потребность полностью.

### Порядок обработки работ

Прежде чем перейти к слоям, важно понять **в каком порядке** работы получают материал.

**Аварийные работы** — всегда первыми, только по дате начала:
```
Аварийная WO-AV-001 | начало 01.06.2026  ← обрабатывается 1-й
Аварийная WO-AV-002 | начало 15.06.2026  ← обрабатывается 2-й
```

**Плановые работы** — после аварийных, по дате начала и приоритету:
```
Приоритет 1 | начало 01.06.2026  ← обрабатывается 3-м
Приоритет 1 | начало 15.06.2026  ← обрабатывается 4-м
Приоритет 2 | начало 01.07.2026  ← обрабатывается 5-м
```

**Почему это важно?** При нехватке материала работа, обрабатываемая раньше, забирает остаток. Порядок — это фактически «очередь» за дефицитными ресурсами.

---

### Слой 1 — Списание (WriteOff)

**Что это?** Документально подтверждённые списания из SAP. Материал уже «закрыт» в системе — он физически израсходован и проведён через бухгалтерию.

**Источник данных:** файл `sample_writeoffs.xlsx`, команда `import-writeoffs`.

```
Работа WO-001 | Кабель ВВГ 3х6
  Документ СП-000001 | списано 50 м | 01.03.2026
  Документ СП-000002 | списано 30 м | 10.03.2026
  Итого по слою 1: покрыто 80 м (из потребности 150 м)
  Остаток: 70 м → передаётся в слой 2
```

**Важно:** этот слой только читает данные — остатки складов НЕ меняются, потому что материал уже израсходован ранее.

---

### Слой 2 — Выдано не списано (IssuedNotWrittenOff)

**Что это?** Материал физически выдан рабочим (они его уже держат в руках), но бухгалтерское списание ещё не проведено. Часто это ситуация на конец периода.

**Источник данных:** файл `sample_issued.xlsx`, команда `import-issued`.

```
Работа WO-001 | Кабель ВВГ 3х6
  Выдано 15.03.2026: 40 м (склад SKL-ALM-01, инфо)
  Итого по слою 2: покрыто 40 м
  Остаток: 30 м → передаётся в слой 3
```

**Важно:** этот слой тоже только читает данные — остатки складов НЕ уменьшаются, потому что физически материал уже ушёл в работу.

---

### Слой 3 — Склад своего завода/филиала

**Что это?** Живые остатки на складах. Алгоритм ищет партии, применяет FIFO и резервирует.

**FIFO — First In First Out (первым пришёл, первым ушёл):**
```
Партия A: поступила 01.01.2026, 100 м → используется первой  (старее)
Партия B: поступила 15.02.2026, 200 м → используется второй  (новее)
```

**Зачем FIFO?** Старые партии лежат дольше, у них выше риск порчи или истечения срока годности. Стандарт бухгалтерского учёта (МСФО/РСБУ).

**Приоритет складов внутри слоя 3:**
```
Сначала: склады того же ЗАВОДА (Plant), что и работа
Потом:   склады того же ФИЛИАЛА (другой завод)
```

```
Работа WO-001 | Завод KZ01 | Филиал Алматы
  SKL-KZ01-01 (завод KZ01) ← приоритет 1, взяли 30 м
  SKL-ALM-02  (филиал Алматы, завод KZ02) ← приоритет 2, нет остатков
  Итого по слою 3: покрыто 30 м
  Остаток: 0 м ✓ ПОТРЕБНОСТЬ ЗАКРЫТА
```

**После слоя 3 остатки складов УМЕНЬШАЮТСЯ** — это реальное резервирование.

---

### Слой 4 — Поставки (по филиалу)

**Что это?** Материалы «в пути» — подтверждённые или уже отгруженные поставки, которые придут на склад своего филиала.

**Условие:** поставка должна быть адресована тому же **филиалу**, что и работа. Логика: смысл поставки в другой филиал — это уже логистика и отдельный процесс.

```
Работа WO-002 | Филиал Астана | Труба 219×10
  Поставка ДОГ-2026-003 (филиал Астана) | ожидается 01.06.2026 | 200 м → резервируем 200 м
  Поставка ДОГ-2026-007 (филиал Астана) | ожидается 15.06.2026 | 100 м → резервируем 50 м
  Итого по слою 4: покрыто 250 м (из остатка 250 м)
  Остаток: 0 м ✓ ПОТРЕБНОСТЬ ЗАКРЫТА
```

---

### Слой 5 — К закупу (Дефицит)

**Что это?** Если после всех 4 слоёв потребность не закрыта — создаётся запись дефицита. Это список позиций, которые нужно закупать.

```
Работа WO-003 | Клапан 1" PN16 | нужно 10 шт
  Слои 1-4: покрыто 0 шт
  → Дефицит: 10 шт | оценочная стоимость: 450 000 тг (10 × 45 000 прогнозная цена)
```

**Прогнозная цена** (`prognosnaya_tsena`) загружается из файла потребностей и используется для оценки стоимости дефицита.

---

### Расчёт обеспечённости

```
Обеспечённость (%) = Закрытая стоимость / (Потребность × Прогнозная цена) × 100

Где:
  Закрытая стоимость = сумма по слоям 1-4 (кол-во × фактическая цена)
  Потребность × Прогнозная цена = плановая стоимость всей потребности
```

Если прогнозная цена не задана (= 0), обеспечённость считается по количеству:
```
Обеспечённость (%) = Закрытое количество / Потребность × 100
```

---

### Ключевые гарантии алгоритма

| Гарантия | Как обеспечивается |
|----------|--------------------|
| Нет отрицательных остатков | `allocate = min(remaining, available)` |
| Нет превышения потребности | `remaining -= allocated` после каждого шага |
| Нет двойного распределения | Кэш доступности в памяти (`_batch_cache`, `_supply_cache`) |
| Разные цены — разные строки | Одна запись на каждую партию |
| Слои 1-2 не меняют склад | Только читают предварительно загруженный кэш |

## 3. Аварийные работы — особый режим

**Аварийные работы** — это внеплановые работы с наивысшим приоритетом (например, аварийный ремонт трубопровода, срочное восстановление оборудования).

### Как они отличаются от плановых

| Параметр | Плановые работы | Аварийные работы |
|----------|----------------|-----------------|
| Файл загрузки | `import-requirements` | `import-emergency` |
| Поле в БД | `is_emergency = False` | `is_emergency = True` |
| Позиция в очереди | После всех аварийных | ВСЕГДА первыми |
| Сортировка | Приоритет → Дата начала | ТОЛЬКО Дата начала |
| Поле `prioritet` | Учитывается | Игнорируется |

### Почему для аварийных нет приоритета

Аварийная работа = уже ЧП. Когда горит труба — не время делить «приоритет 1» и «приоритет 2». Все аварийные работы равнозначны по срочности, и порядок их обработки определяется только тем, **когда** началась авария.

### Загрузка аварийных работ

```bash
# Загрузить аварийные работы из отдельного файла
python main.py import-emergency data/emergency_works.xlsx

# Если аварийная работа уже есть в БД (загружена через import-requirements),
# повторный import-emergency обновит её флаг is_emergency = True
```

```
PythonProject/

├── app/                            ← Основное приложение

│   │
│   ├── models/                     ← Схемы данных (Pydantic)

├── data/

│   └── exports/                    ← Результаты (создаются автоматически)
│
├── logs/                           ← Файлы логов (создаются автоматически)
│
├── main.py                         ← Точка входа, CLI-команды (Typer)
├── pyproject.toml                  ← Конфигурация проекта, зависимости, ruff, pytest

```

### Принцип слоёной архитектуры

```
CLI (main.py)
     ↓  вызывает
Services (import_service, export_service)
     ↓  вызывает
Allocation Engine (engine.py)
     ↓  вызывает
Repositories (work_repository, material_repository)
     ↓  работает с
Database (SQLAlchemy ORM → PostgreSQL)
```

Каждый слой знает только о слое ниже. Это позволяет:
- Менять реализацию слоя без изменения остальных
- Тестировать каждый слой отдельно
- Легко добавлять новые источники данных (SAP API, другие форматы)

## 6. Быстрый старт

```bash
# 1. Клонировать репозиторий
git clone https://github.com/your-org/maps.git
cd maps

# 2. Создать виртуальное окружение Python
python -m venv .venv
source .venv/bin/activate        # Linux / macOS
# .venv\Scripts\activate         # Windows

# 3. Установить все зависимости
pip install -e ".[dev]"

# 4. Скопировать конфигурацию и заполнить
cp .env.example .env
nano .env   # Указать параметры PostgreSQL

# 5. Создать базу данных и все таблицы
python main.py init

# 6. Сгенерировать тестовые данные (6 Excel-файлов)
python scripts/generate_sample_data.py

# 7. Загрузить данные в правильном порядке
python main.py import-requirements data/sample_requirements.xlsx  # потребности + прогнозные цены
python main.py import-emergency data/sample_emergency.xlsx        # аварийные работы (отдельный файл)
python main.py import-stock data/sample_stock.xlsx                # остатки складов
python main.py import-supplies data/sample_supplies.xlsx          # поставки в пути
python main.py import-writeoffs data/sample_writeoffs.xlsx        # списания из SAP
python main.py import-issued data/sample_issued.xlsx              # выдано не списано

# 8. Проверить состояние загруженных данных
python main.py status

# 9. Запустить распределение
python main.py allocate

# 10. Экспортировать результаты в Excel
python main.py export <SESSION_ID>    # ID из вывода предыдущей команды
```

## 7. Подробная инструкция по установке

### Требования к системе

- **Python 3.12 или выше**
  ```bash
  python --version    # Должно быть Python 3.12+
  ```

- **PostgreSQL 14 или выше**
  ```bash
  psql --version      # Должно быть 14+
  ```

### Создание базы данных PostgreSQL

```sql
-- Подключиться к PostgreSQL под суперпользователем
psql -U postgres

-- Создать пользователя системы
CREATE USER maps_user WITH PASSWORD 'придумайте_пароль';

-- Создать базу данных
CREATE DATABASE maps_db OWNER maps_user;

-- Дать права
GRANT ALL PRIVILEGES ON DATABASE maps_db TO maps_user;

-- Выйти
\q
```

### Заполнение .env файла

```bash
# Параметры подключения к PostgreSQL
DB_HOST=localhost          # Для локальной разработки
DB_PORT=5432               # Стандартный порт PostgreSQL
DB_NAME=maps_db            # Имя базы (создали выше)
DB_USER=maps_user          # Пользователь (создали выше)
DB_PASSWORD=придумайте     # Пароль (создали выше)

# Настройки приложения
APP_ENV=development        # В production меняем на "production"
LOG_LEVEL=INFO             # DEBUG — подробно, INFO — стандартно
DATA_DIR=data              # Папка с Excel-файлами
EXPORT_DIR=data/exports    # Куда сохранять результаты
```

### Настройка pre-commit (один раз)

```bash
pre-commit install
# Теперь ruff будет проверять код автоматически перед каждым git commit
```

## 8. Формат входных данных Excel

### Файл потребностей (`import-requirements`)

Каждая строка = потребность одной работы в одном материале.
Одна работа может занимать несколько строк (разные материалы).

| Колонка | Тип | Обязательна | Пример | Описание |
|---------|-----|:-----------:|--------|----------|
| Код работы | Текст | ✅ | `WO-001` | Уникальный код работы |
| Системный номер | Текст | ✅ | `000000000010010001` | SAP-номер материала |
| Потребность | Число | ✅ | `150.5` | Нужное количество (строго > 0) |
| Прогнозная цена | Число | | `15000.00` | Цена единицы для расчёта обеспечённости |
| Тип работы | Текст | | `Ремонт` | Тип/вид работы |
| Филиал | Текст | | `Алматы` | Филиал компании |
| Подразделение | Текст | | `Цех 3` | Подразделение |
| Центр затрат | Текст | | `CC-KZ01-101` | Центр затрат SAP |
| Завод | Текст | | `KZ01` | Код завода (Plant в SAP) |
| Дата начала | Дата | | `2026-06-01` | Формат YYYY-MM-DD |
| Дата окончания | Дата | | `2026-07-31` | Должна быть ≥ даты начала |
| Приоритет | Число | | `2` | 1 (высший), 2 (средний), 3 (низший) |
| Наименование материала | Текст | | `Кабель ВВГ 3х2,5` | Для справки |
| Ед.изм | Текст | | `м` | Единица измерения |

> **Прогнозная цена** — важна для расчёта обеспечённости по стоимости. Если не указана, считается обеспечённость по количеству.

---

### Файл аварийных работ (`import-emergency`)

Формат идентичен файлу потребностей. Отличие одно: все загруженные работы получают флаг `is_emergency = True` и автоматически становятся во главе очереди.

Рекомендуется использовать **отдельный файл** для аварийных работ — это упрощает контроль и аудит.

> ⚠️ **Важно:** Если аварийная работа уже есть в БД (загружена через `import-requirements`), повторная загрузка через `import-emergency` установит ей флаг аварийности без дублирования записи.

## 10. Структура базы данных

### Входные таблицы (заполняются при импорте)

| Таблица | Описание | Ключевые поля |
|---------|----------|---------------|
| `works` | Строительно-монтажные работы | `is_emergency` — флаг аварийности |
| `materials` | Справочник материалов | `sys_nomer` — SAP-номер |
| `requirements` | Потребности: какая работа требует что и сколько | `prognosnaya_tsena` — прогнозная цена |
| `warehouses` | Справочник складов | `filial`, `zavod` |
| `stock_batches` | Партии материалов (снимок склада) | `data_postupleniya` для FIFO |
| `supplies` | Строки поставок | `filial` для фильтрации по филиалу |
| `writeoffs` | Списания из SAP (Слой 1) | `nomer_dokumenta`, `data_spisaniya` |
| `issued_not_written_off` | Выдано не списано (Слой 2) | `warehouse_id` информационно |

### Выходные таблицы (заполняются алгоритмом)

| Таблица | Описание |
|---------|----------|
| `allocation_sessions` | История запусков: ID сессии, дата, параметры |
| `allocation_results` | Строки распределения с `istochnik`: `spisanie`, `vydano`, `sklad`, `vozmozhnoe_sklad`, `postavka` |
| `stock_movements` | Движения по складам: расходы каждой партии |
| `deficit_records` | Дефицит: что нужно закупить, оценочная стоимость |

### Значения поля `istochnik` (источник покрытия)

| Значение | Слой | Описание |
|----------|------|----------|
| `spisanie` | 1 | Списание из SAP |
| `vydano` | 2 | Выдано физически, не списано |
| `sklad` | 3 | Склад своего завода/филиала |
| `vozmozhnoe_sklad` | — | Склад другого филиала (только анализ, не резервирование) |
| `postavka` | 4 | Поставка в пути (своего филиала) |

### Схема связей

```
works ────────────────── requirements ──── materials
  │                           │                │
  │ (is_emergency)            │           stock_batches ── warehouses
  │                           │
  ├── writeoffs ──────────────┤
  │                           │
  └── issued_not_written_off ─┤
                              │
allocation_sessions ──────────┤
        │                     │
        ├── allocation_results (istochnik: 5 типов)
        ├── stock_movements
        └── deficit_records
```

## 14. Частые вопросы

**Q: Почему PostgreSQL, а не SQLite?**

PostgreSQL рассчитан на параллельную работу нескольких пользователей и большие объёмы (1 млн+ строк остатков). SQLite работает только с одним пользователем одновременно и не подходит для production.

---

**Q: Почему `Decimal`, а не `float` для количеств и стоимостей?**

`float` имеет ошибки округления: `0.1 + 0.2 = 0.30000000000000004`. В финансовых расчётах это приводит к расхождениям. `Decimal` точен до указанного знака.

---

**Q: Что такое FIFO и зачем он нужен?**

First In First Out — «первым пришёл, первым ушёл». Партия, которая поступила на склад раньше, списывается первой. Это стандартный метод учёта в бухгалтерии (МСФО IAS 2).

---

**Q: Зачем нужны слои 1 и 2, если материал уже использован?**

Они показывают **реальную картину**:
- Слой 1 (Списание): материал официально «закрыт» в SAP — зафиксированный факт
- Слой 2 (Выдано): материал у рабочих — они уже работают — это тоже покрытие

Без этих слоёв алгоритм думал бы, что потребность не покрыта, и дважды пытался бы выделить материал.

---

**Q: Почему поставки фильтруются по филиалу, а не по заводу?**

Поставка — это логистическая единица, привязанная к филиалу. Одна компания может иметь несколько заводов в одном филиале. Поставка адресована филиалу (точке доставки), а не конкретному заводу.

---

**Q: Что такое «сессия распределения»?**

Каждый запуск `python main.py allocate` создаёт новую сессию с уникальным ID. Это позволяет хранить историю нескольких запусков и сравнивать сценарии. Например: «что если изменить приоритеты?» — запускаем новую сессию и сравниваем результаты.

**Q: Как адаптировать колонки Excel под свой формат?**

Откройте `app/services/import_service.py` и найдите словари соответствия:
- `REQUIREMENTS_COLUMN_MAP` — для файла потребностей
- `STOCK_COLUMN_MAP` — для файла остатков
- `SUPPLY_COLUMN_MAP` — для файла поставок
- `WRITEOFF_COLUMN_MAP` — для файла списаний
- `ISSUED_COLUMN_MAP` — для файла выдано не списано

Измените ключи словарей (левая часть) на названия ваших колонок. Значения (правая часть) — внутренние имена системы, не менять.

**Q: Что означает «Возможное перемещение» в отчёте?**

Это склады **других филиалов**, на которых есть нужный материал. Алгоритм фиксирует их как `vozmozhnoe_sklad` — возможный, но не задействованный источник. Это подсказка для логиста: «если везти из Астаны в Алматы — вот откуда».
