## 1. Что делает система

MAPS решает задачу: **кому и откуда дать материалы при ограниченных ресурсах**.

Представьте ситуацию:
- 500 строительных работ требуют материалы
- На складах есть партии разных дат и цен
- Часть материалов ещё «в пути» (поставки)
- Некоторых материалов не хватает (дефицит)
- Работы имеют разные приоритеты и сроки

Вручную это решить за разумное время невозможно. MAPS автоматически:

| Задача | Результат |
|--------|-----------|
| Анализирует потребности всех работ | Сводная таблица: кому что нужно |
| Ищет материалы на складах | Соблюдает FIFO и приоритеты складов |
| Резервирует из поставок | Если склада не хватает |
| Фиксирует дефицит | Список позиций «к закупу» |
| Рассчитывает обеспечённость | % покрытия по каждой работе |

## 2. Как работает алгоритм

### Шаг 1 — Сортировка работ

Работы обрабатываются в строгом порядке — от самых важных к менее важным:

```
Приоритет 1 (высший — аварийные, критичные)
  → по дате начала (ранние работы первыми)
    → по филиалу
      → по коду работы

Приоритет 2 (плановые работы)
  → та же логика...

Приоритет 3 (резервные работы)
  → та же логика...
```

**Почему это важно?** При нехватке материала работа с приоритетом 1 получит материал, а работа с приоритетом 3 — нет. Это называется «конкурентное распределение».

---

### Шаг 2 — Фаза 1: Склад

Для каждой потребности ищем партии материала в трёх группах складов (по убыванию приоритета):

```
Группа 1: Склады того же завода (Plant), что и работа  ← используем первыми
Группа 2: Склады того же филиала (другой завод)        ← используем вторыми
Группа 3: Все остальные склады                         ← используем последними
```

Внутри каждой группы — строгий **FIFO** (First In First Out):

```
Партия A: поступила 01.01.2026, 100 м → используется первой  (старее)
Партия B: поступила 15.02.2026, 200 м → используется второй  (новее)
```

**Зачем FIFO?** Старые партии лежат дольше, у них выше риск порчи или истечения срока годности. Стандарт бухгалтерского учёта (МСФО/РСБУ).

---

### Шаг 3 — Фаза 2: Поставки

Если после склада потребность не закрыта — смотрим на поставки «в пути». Сортируем по дате ожидаемой поставки (ближайшие — первые):

```
Поставка ДОГ-001: ожидается 01.06.2026, 500 м  → резервируем первой
Поставка ДОГ-002: ожидается 15.06.2026, 200 м  → резервируем второй
```

---

### Шаг 4 — Фаза 3: Дефицит

Если склад + поставки всё равно не покрыли потребность — создаётся запись дефицита:

```
Работа WO-001 | Кабель ВВГ 3х6 | дефицит 150 м → К ЗАКУПУ
```

---

### Ключевые гарантии алгоритма

| Гарантия | Как обеспечивается |
|----------|--------------------|
| Нет отрицательных остатков | `allocate = min(remaining, available)` |
| Нет превышения потребности | `remaining -= allocated` после каждого шага |
| Нет двойного распределения | Кэш доступности в памяти (`_batch_cache`) |
| Разные цены — разные строки | Одна запись на каждую партию |

## 3. Архитектура и структура проекта

```
PythonProject/
│
├── app/                            ← Основное приложение
│   ├── core/                       ← Ядро: конфигурация и логирование
│   │   ├── config.py               ← Настройки из .env (БД, пути, уровень лога)
│   │   └── logging_config.py       ← Логи в файл + консоль одновременно
│   │
│   ├── db/                         ← База данных
│   │   ├── database.py             ← Подключение к PostgreSQL, фабрика сессий
│   │   └── models.py               ← 10 таблиц БД (ORM-модели SQLAlchemy)
│   │
│   ├── models/                     ← Схемы данных (Pydantic)
│   │   └── schemas.py              ← Валидация строк при импорте из Excel
│   │
│   ├── repositories/               ← Слой работы с БД (паттерн Repository)
│   │   ├── base.py                 ← Базовый CRUD: get, add, delete, count
│   │   ├── work_repository.py      ← Работы и потребности
│   │   └── material_repository.py  ← Материалы, партии, поставки
│   │
│   ├── allocation/                 ← Алгоритм распределения
│   │   └── engine.py               ← Движок: FIFO, приоритеты, дефицит
│   │
│   └── services/                   ← Сервисы ввода/вывода
│       ├── import_service.py       ← Excel → PostgreSQL
│       └── export_service.py       ← PostgreSQL → Excel (4 листа)
│
├── tests/                          ← Автоматические тесты (pytest)
│   └── test_allocation.py          ← Тесты схем и алгоритма
│
├── scripts/
│   └── generate_sample_data.py     ← Генерация тестовых Excel-файлов
│
├── data/
│   ├── templates/                  ← Шаблоны Excel для заполнения
│   └── exports/                    ← Результаты (создаются автоматически)
│
├── logs/                           ← Файлы логов (создаются автоматически)
│
├── main.py                         ← Точка входа, CLI-команды (Typer)
├── pyproject.toml                  ← Конфигурация проекта, зависимости, ruff, pytest
├── .env.example                    ← Шаблон .env (скопировать и заполнить)
├── .pre-commit-config.yaml         ← Git-хуки: ruff перед каждым коммитом
└── .gitignore                      ← Что не попадает в git
```

### Принцип слоёной архитектуры

```
CLI (main.py)
     ↓  вызывает
Services (import_service, export_service)
     ↓  вызывает
Allocation Engine (engine.py)
     ↓  вызывает
Repositories (work_repository, material_repository)
     ↓  работает с
Database (SQLAlchemy ORM → PostgreSQL)
```

Каждый слой знает только о слое ниже. Это позволяет:
- Менять реализацию слоя без изменения остальных (например, заменить PostgreSQL на другую СУБД)
- Тестировать каждый слой отдельно
- Легко добавлять новые источники данных (SAP API, другие форматы)

## 5. Быстрый старт

```bash
# 1. Клонировать репозиторий
git clone https://github.com/your-org/maps.git
cd maps

# 2. Создать виртуальное окружение Python
python -m venv .venv
source .venv/bin/activate        # Linux / macOS
# .venv\Scripts\activate         # Windows

# 3. Установить все зависимости
pip install -e ".[dev]"

# 4. Скопировать конфигурацию и заполнить
cp .env.example .env
nano .env   # Указать параметры PostgreSQL

# 5. Создать базу данных и таблицы
python main.py init

# 6. Сгенерировать тестовые данные
python scripts/generate_sample_data.py

# 7. Загрузить данные
python main.py import-requirements data/sample_requirements.xlsx
python main.py import-stock data/sample_stock.xlsx
python main.py import-supplies data/sample_supplies.xlsx

# 8. Запустить распределение
python main.py allocate

# 9. Экспортировать результаты в Excel
python main.py export <SESSION_ID>    # ID из вывода предыдущей команды
```

## 6. Подробная инструкция по установке

### Требования к системе

- **Python 3.11 или выше**
  ```bash
  python --version    # Должно быть Python 3.11+
  ```

- **PostgreSQL 14 или выше**
  ```bash
  psql --version      # Должно быть 14+
  ```

### Создание базы данных PostgreSQL

```sql
-- Подключиться к PostgreSQL под суперпользователем
psql -U postgres

-- Создать пользователя системы
CREATE USER maps_user WITH PASSWORD 'придумайте_пароль';

-- Создать базу данных
CREATE DATABASE maps_db OWNER maps_user;

-- Дать права
GRANT ALL PRIVILEGES ON DATABASE maps_db TO maps_user;

-- Выйти
\q
```

### Заполнение .env файла

```bash
# Параметры подключения к PostgreSQL
DB_HOST=localhost          # Для локальной разработки
DB_PORT=5432               # Стандартный порт PostgreSQL
DB_NAME=maps_db            # Имя базы (создали выше)
DB_USER=maps_user          # Пользователь (создали выше)
DB_PASSWORD=придумайте     # Пароль (создали выше)

# Настройки приложения
APP_ENV=development        # В production меняем на "production"
LOG_LEVEL=INFO             # DEBUG — подробно, INFO — стандартно
DATA_DIR=data              # Папка с Excel-файлами
EXPORT_DIR=data/exports    # Куда сохранять результаты
```

### Настройка pre-commit (один раз)

```bash
pre-commit install
# Теперь ruff будет проверять код автоматически перед каждым git commit
```

## 7. Формат входных данных Excel

### Файл потребностей (`import-requirements`)

Каждая строка = потребность одной работы в одном материале.
Одна работа может занимать несколько строк (разные материалы).

| Колонка | Тип | Обязательна | Пример | Описание |
|---------|-----|:-----------:|--------|----------|
| Код работы | Текст | ✅ | `WO-001` | Уникальный код работы из SAP |
| Системный номер | Текст | ✅ | `000000000010010001` | SAP-номер материала (18 знаков) |
| Потребность | Число | ✅ | `150.5` | Нужное количество (строго > 0) |
| Тип работы | Текст | | `Ремонт` | Тип/вид работы |
| Филиал | Текст | | `Алматы` | Филиал компании |
| Подразделение | Текст | | `Цех 3` | Подразделение |
| Центр затрат | Текст | | `CC-KZ01-101` | Центр затрат SAP |
| Завод | Текст | | `KZ01` | Код завода (Plant в SAP) |
| Дата начала | Дата | | `2026-06-01` | Формат YYYY-MM-DD |
| Дата окончания | Дата | | `2026-07-31` | Должна быть ≥ даты начала |
| Приоритет | Число | | `2` | 1 (высший), 2 (средний), 3 (низший) |
| Наименование материала | Текст | | `Кабель ВВГ 3х2,5` | Для справки |
| Ед.изм | Текст | | `м` | Единица измерения |

---

### Файл складских остатков (`import-stock`)

Каждая строка = одна партия материала на одном складе.

> ⚠️ **Внимание:** При импорте все существующие остатки заменяются. Это «снимок склада» на текущий момент.

| Колонка | Тип | Обязательна | Пример |
|---------|-----|:-----------:|--------|
| Код склада | Текст | ✅ | `SKL-ALM-01` |
| Системный номер | Текст | ✅ | `000000000010010001` |
| Количество | Число | ✅ | `500.0` |
| Номер партии | Текст | | `P-2026-001` |
| Стоимость за ед | Число | | `1500.00` |
| Дата поступления | Дата | | `2026-01-15` |
| Тип склада | Текст | | `центральный` |
| Филиал склада | Текст | | `Алматы` |
| Завод склада | Текст | | `KZ01` |
| Наименование материала | Текст | | `Кабель ВВГ 3х2,5` |
| Ед.изм | Текст | | `м` |
| Группа материала | Текст | | `Кабели` |

---

### Файл поставок (`import-supplies`)

Каждая строка = один материал в одной поставке.

| Колонка | Тип | Обязательна | Пример |
|---------|-----|:-----------:|--------|
| Системный номер | Текст | ✅ | `000000000010010001` |
| Количество | Число | ✅ | `1000.0` |
| Договор | Текст | | `ДОГ-2026-001` |
| Поставщик | Текст | | `ТОО Стройснаб-KZ` |
| Код склада | Текст | | `SKL-ALM-01` |
| Филиал | Текст | | `Алматы` |
| Завод | Текст | | `KZ01` |
| Дата поставки | Дата | | `2026-06-15` |
| Стоимость за ед | Число | | `1400.00` |
| Статус | Текст | | `confirmed` |

Допустимые статусы: `confirmed` (подтверждено), `in_transit` (груз отправлен).

## 8. Команды CLI

### `python main.py init`

Создаёт все таблицы в PostgreSQL. Запускать **один раз** при первом запуске.
Безопасно вызывать повторно — данные не удаляет.

```bash
python main.py init
```

---

### `python main.py import-requirements FILE`

Импортирует потребности работ из Excel.

```bash
python main.py import-requirements data/requirements.xlsx
python main.py import-requirements data/requirements.xlsx --sheet "Потребности"
```

---

### `python main.py import-stock FILE`

Импортирует складские остатки. **Полностью заменяет** существующие остатки.

```bash
python main.py import-stock data/stock.xlsx
```

---

### `python main.py import-supplies FILE`

Импортирует поставки. **Полностью заменяет** существующие поставки.

```bash
python main.py import-supplies data/supplies.xlsx
```

---

### `python main.py allocate`

Запускает алгоритм распределения. Каждый запуск — новая сессия.

```bash
python main.py allocate
python main.py allocate --session "сценарий_июнь_2026"
```

Пример вывода:
```

  └──────────────────────────┴───────┘

Для экспорта в Excel:
  maps export 20260523_143000_abc12
```

### `python main.py export SESSION_ID`

Экспортирует результаты в Excel-файл с 4 листами.

Показывает текущее состояние БД: количество записей и последние сессии.

```bash

```

## 9. Структура базы данных

### Входные таблицы (заполняются при импорте)

| Таблица | Описание |
|---------|----------|
| `works` | Строительно-монтажные работы |
| `materials` | Справочник материалов (номенклатура SAP) |
| `requirements` | Потребности: какая работа требует какой материал и сколько |
| `warehouses` | Справочник складов |
| `stock_batches` | Партии материалов на складах (с датой для FIFO) |
| `supplies` | Заказы на поставку (шапка документа) |
| `supply_lines` | Строки поставок: какой материал, сколько, по какой цене |

### Выходные таблицы (заполняются алгоритмом)

| Таблица | Описание |
|---------|----------|
| `allocation_sessions` | История запусков распределения |
| `allocation_results` | Строки распределения: кому, откуда, сколько, по какой цене |
| `stock_movements` | Движения по складам: расходы каждой партии |
| `deficit_records` | Дефицит: что нужно закупить |

### Схема связей

```
works ────────────── requirements ──── materials
                          │                 │
                          │            stock_batches ── warehouses
                          │
allocation_sessions ──────┤
        │                 │
        ├── allocation_results
        ├── stock_movements
        └── deficit_records
```

## 10. Результаты работы системы

### Что записывается в БД после `maps allocate`

После запуска алгоритма в таблицах появятся:

**`allocation_results`** — главная таблица результатов:
```
Работа WO-001 | Кабель ВВГ | склад SKL-ALM-01 | партия P-001 | 100 м | 1500 тг/м | 150 000 тг
Работа WO-001 | Кабель ВВГ | склад SKL-ALM-01 | партия P-002 |  50 м | 1600 тг/м |  80 000 тг
Работа WO-002 | Труба      | поставка ДОГ-001 |             | 200 м | 3000 тг/м | 600 000 тг
Работа WO-003 | Клапан     | К закупу         |             |  10 шт|           |
```

**`deficit_records`** — что нужно закупить:
```
Работа WO-003 | Клапан 1" | 10 шт | нужно к 31.07.2026
```

### Excel-отчёт (4 листа)

| Лист | Содержание |
|------|-----------|
| **Распределение** | Полная таблица: работа → материал → источник → партия → количество → стоимость |
| **Движение склада** | Расходы по каждой партии: склад, материал, партия, изменение, остаток |
| **Дефицит** | Позиции к закупу: работа, материал, количество, нужно к дате |
| **Обеспеченность** | % покрытия каждой потребности: распределено / потребность × 100% |

## 13. Частые вопросы

**Q: Почему PostgreSQL, а не SQLite?**

PostgreSQL рассчитан на параллельную работу нескольких пользователей и большие объёмы (1 млн+ строк остатков). SQLite работает только с одним пользователем одновременно и не подходит для production.

---

**Q: Почему `Decimal`, а не `float` для количеств и стоимостей?**

`float` имеет ошибки округления: `0.1 + 0.2 = 0.30000000000000004`. В финансовых расчётах это приводит к расхождениям. `Decimal` точен до указанного знака.

---

**Q: Что такое FIFO и зачем он нужен?**

First In First Out — «первым пришёл, первым ушёл». Партия, которая поступила на склад раньше, списывается первой. Это стандартный метод учёта в бухгалтерии (МСФО IAS 2).

---

**Q: Что такое «сессия распределения»?**

Каждый запуск `maps allocate` создаёт новую сессию с уникальным ID. Это позволяет хранить историю нескольких запусков и сравнивать сценарии. Например: «что если изменить приоритеты?» — запускаем новую сессию и сравниваем результаты.

---

**Q: Как адаптировать колонки Excel под свой формат?**

Откройте `app/services/import_service.py` и найдите словари:
- `REQUIREMENTS_COLUMN_MAP` — для файла потребностей
- `STOCK_COLUMN_MAP` — для файла остатков
- `SUPPLY_COLUMN_MAP` — для файла поставок

Измените ключи словарей на названия ваших колонок.

---

**Q: Можно ли запускать распределение по одному филиалу?**

В текущей версии MVP — нет, распределение запускается по всей базе. В Этапе 2 будет добавлена фильтрация по филиалу/заводу.
